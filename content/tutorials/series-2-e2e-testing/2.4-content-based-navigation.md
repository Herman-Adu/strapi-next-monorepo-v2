## Problem Statement

Your Playwright tests fail intermittently when navigating between pages in Next.js dev mode. Tests timeout waiting for `domcontentloaded` or `networkidle` events that never fire when Hot Module Replacement (HMR) is active.

**Symptoms:**

- Navigation timeouts: `page.goto('/about', { waitUntil: 'domcontentloaded' })` hangs
- Works in production builds but fails in dev mode
- **6 tests** affected by navigation timing issues
- Error: `Navigation timeout of 60000ms exceeded`

**Why This Matters:**
E2E tests should run in dev mode (faster feedback) AND production mode (realistic validation). Tests that only work in one environment aren't reliable.

## Understanding the Problem

### DOM Lifecycle Events in Next.js

```typescript
// ❌ FAILS in dev mode: domcontentloaded never fires
test("navigate to about page", async ({ page }) => {
  await page.goto("/about", {
    waitUntil: "domcontentloaded",
  })
  // Error: Navigation timeout of 60000ms exceeded
})

// ❌ ALSO FAILS: networkidle is unreliable with HMR websocket
test("navigate to about page", async ({ page }) => {
  await page.goto("/about", {
    waitUntil: "networkidle",
  })
  // Hangs waiting for HMR websocket to idle (never happens)
})
```

**Why traditional wait strategies fail:**

1. **Hot Module Replacement (HMR):**

   - Webpack dev server maintains websocket connection
   - Constantly sends ping/pong messages
   - `networkidle` never achieved (network never "idle")

2. **Client-Side Routing:**

   - Next.js App Router navigates via JavaScript
   - `domcontentloaded` fires ONCE on initial load
   - Subsequent navigations don't trigger DOM events

3. **Hydration Timing:**
   - React hydrates after initial HTML render
   - Content may appear before hydration completes
   - DOM events fire before content is interactive

### Real-World Failure Pattern

```bash
$ yarn test:e2e homepage.spec.ts --project=chromium

Running 1 test using 1 worker
[chromium] › homepage.spec.ts:10:1 › Homepage

⠙  [chromium] › homepage.spec.ts:10:1 › Homepage
   Waiting for navigation... (60s)

✗ [chromium] › homepage.spec.ts:10:1 › Homepage (60.1s)
   Error: Navigation timeout of 60000ms exceeded
```

## Solution: Wait for Actual Content

### Strategy: Content Visibility Over Events

Instead of waiting for browser events (unreliable), wait for actual page content to appear (reliable):

```typescript
// ✅ RELIABLE: Wait for actual content
test("navigate to about page", async ({ page }) => {
  // Navigate WITHOUT waiting for events
  await page.goto("/about")

  // Wait for expected content to be visible
  await page.locator("text=/About Us/i").waitFor({ state: "visible" })
})
```

**Why this works:**

✅ **Content is the source of truth** (what users see)  
✅ **Works in dev AND production** (independent of build mode)  
✅ **Handles hydration** (waits for interactive content)  
✅ **Ignores HMR noise** (websocket doesn't affect content)

### Step 1: Basic Content-Based Navigation

```typescript
// tests/utils/navigation-helpers.ts

import { Page } from "@playwright/test"

/**
 * Navigate to a page and wait for expected content
 *
 * @param page - Playwright page object
 * @param url - URL to navigate to
 * @param expectedContent - Text or regex to wait for
 * @param timeout - Max wait time in ms (default: 15000)
 */
export async function navigateAndWaitForContent(
  page: Page,
  url: string,
  expectedContent: string | RegExp,
  timeout = 15000
): Promise<void> {
  // Navigate without waiting for events
  await page.goto(url)

  // Wait for expected content to appear
  const selector =
    typeof expectedContent === "string"
      ? `text=${expectedContent}`
      : `text=${expectedContent}`

  await page.waitForSelector(selector, {
    state: "visible",
    timeout,
  })
}
```

**Usage:**

```typescript
// tests/about.spec.ts
import { test, expect } from "@playwright/test"
import { navigateAndWaitForContent } from "./utils/navigation-helpers"

test("about page loads correctly", async ({ page }) => {
  // ✅ Wait for "About Us" heading
  await navigateAndWaitForContent(page, "/about", /About Us/i)

  // Content is now visible and interactive
  await expect(page.locator("h1")).toContainText("About Us")
})

test("contact page loads correctly", async ({ page }) => {
  // ✅ Wait for "Contact" heading
  await navigateAndWaitForContent(page, "/contact", /Contact/i)

  await expect(page.locator("form")).toBeVisible()
})
```

### Step 2: Enhanced Helper with Fallback Selectors

Some pages might not have predictable text. Use multiple fallback selectors:

```typescript
// tests/utils/navigation-helpers.ts (enhanced)

export async function navigateAndWaitForContent(
  page: Page,
  url: string,
  expectedContent?: string | RegExp,
  options: {
    timeout?: number
    contentTimeout?: number
  } = {}
): Promise<void> {
  // Increase timeout in CI (production builds slower to hydrate)
  const defaultContentTimeout = process.env.CI ? 25000 : 15000
  const { timeout = 60000, contentTimeout = defaultContentTimeout } = options

  // Navigate without waiting for lifecycle events
  await page.goto(url, {
    waitUntil: "domcontentloaded", // Minimal wait
    timeout,
  })

  if (expectedContent) {
    // Wait for specific content
    const selector =
      typeof expectedContent === "string"
        ? `text=${expectedContent}`
        : `text=${expectedContent}`

    await page.waitForSelector(selector, {
      state: "visible",
      timeout: contentTimeout,
    })
  } else {
    // Fallback: Wait for ANY main content
    // Most pages have nav, main content, footer
    await page.waitForSelector('nav, main, [role="main"]', {
      state: "visible",
      timeout: contentTimeout,
    })
  }
}
```

**Usage with fallback:**

```typescript
test("homepage loads", async ({ page }) => {
  // Wait for specific content
  await navigateAndWaitForContent(page, "/", /Welcome|Home/i)
})

test("dashboard loads", async ({ page }) => {
  // No specific text, wait for generic content
  await navigateAndWaitForContent(page, "/dashboard")
  // Waits for nav/main/role=main to appear
})
```


## Common Pitfalls

### ❌ Pitfall #1: Overly Generic Content Selectors

```typescript
// Bad: Too generic (matches too many elements)
await page.locator("text=/the/i").waitFor()
// "the" appears in navigation, footer, etc.

// Good: Specific to page content
await page.locator('h1:has-text("About Us")').waitFor()
```

### ❌ Pitfall #2: Not Handling Hydration

```typescript
// Bad: Content visible but not interactive yet
await page.goto("/contact")
await page.locator("form").waitFor()
await page.fill('[name="email"]', "test@example.com") // Might fail!

// Good: Wait for interactive element
await page.goto("/contact")
await page.locator('input[name="email"]').waitFor({ state: "visible" })
await page.fill('[name="email"]', "test@example.com") // Reliable
```

### ❌ Pitfall #3: Same Content on Multiple Pages

```typescript
// Bad: "Loading..." appears on every page
await page.goto("/dashboard")
await page.locator("text=/Loading/i").waitFor()
// Could match any page!

// Good: Page-specific content
await page.goto("/dashboard")
await page.locator("text=/Dashboard|Your Account/i").waitFor()
```

### ❌ Pitfall #4: Hardcoded Timeout Too Short

```typescript
// Bad: Timeout too short for CI
await page.locator("text=/Products/i").waitFor({ timeout: 3000 })
// CI servers slower, might need 10-15s

// Good: Configurable timeout based on environment
const timeout = process.env.CI ? 25000 : 15000
await page.locator("text=/Products/i").waitFor({ timeout })
```

## Advanced: Combining with Other Patterns

### Wait for Content + API Response

```typescript
async function navigateAndWaitForAPI(
  page: Page,
  url: string,
  apiPattern: string | RegExp,
  contentPattern: string | RegExp
): Promise<void> {
  // Start waiting for API call
  const apiPromise = page.waitForResponse(
    (resp) => resp.url().match(apiPattern) !== null
  )

  // Navigate
  await page.goto(url)

  // Wait for both API and content
  await Promise.all([
    apiPromise,
    page.locator(`text=${contentPattern}`).waitFor(),
  ])
}

// Usage:
await navigateAndWaitForAPI(
  page,
  "/dashboard",
  /\/api\/user/, // API call pattern
  /Welcome back/i // Content pattern
)
```

### Network Idle After Content

```typescript
async function navigateWaitContentThenIdle(
  page: Page,
  url: string,
  contentPattern: string | RegExp
): Promise<void> {
  await page.goto(url)

  // Wait for content first (quick)
  await page.locator(`text=${contentPattern}`).waitFor()

  // Then wait for network to settle (slow but reliable)
  await page.waitForLoadState("networkidle", { timeout: 10000 })
}
```
