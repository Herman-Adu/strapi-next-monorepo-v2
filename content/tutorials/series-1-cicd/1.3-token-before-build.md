## The Problem: "Works Locally, Fails in CI"

### Symptom

```bash
# Local development - WORKS ✅
$ yarn build
✓ Compiling...
✓ Collecting page data...
✓ Generating static pages (15/15)
✓ Build completed successfully

$ yarn start
Server running on http://localhost:3000

# GitHub Actions CI - FAILS ❌
Run yarn workspace @repo/ui build
✓ Compiling...
✗ Error: STRAPI_REST_READONLY_API_KEY is not defined
  at fetch (app/blog/[slug]/page.tsx:12)
```

### The Confusion

**Developer's mental model:**

> "Environment variables are runtime configuration. I set them in the workflow before tests run, so they should be available."

**Reality:**

> "Next.js SSR routes execute fetch() during BUILD TIME to pre-render pages. Variables must exist BEFORE the build step."

## Understanding Next.js Build-Time Behavior

### When Does Next.js Read Environment Variables?

```typescript
// app/blog/[slug]/page.tsx - Next.js App Router

export default async function BlogPost({ params }: { params: { slug: string } }) {
  // ⚠️ THIS CODE RUNS AT BUILD TIME, NOT JUST AT RUNTIME!
  const response = await fetch(
    `${process.env.NEXT_PUBLIC_STRAPI_URL}/api/blogs/${params.slug}`,
    {
      headers: {
        Authorization: `Bearer ${process.env.STRAPI_REST_READONLY_API_KEY}`,
        // ↑ If undefined during build → 401 error baked into static output
      },
    }
  )

  const blog = await response.json()
  return <Article data={blog} />
}
```

### The Build Process

```bash
$ yarn build

# What happens:
1. ✅ TypeScript compilation (tsc)
2. ✅ Client-side bundling (webpack/turbopack)
3. ✅ SERVER-SIDE RENDERING (fetch() executes!)
   - Reads process.env.STRAPI_REST_READONLY_API_KEY
   - Makes API call to fetch blog data
   - Generates static HTML
4. ✅ Static page optimization
5. ✅ Build manifest creation

# If STRAPI_REST_READONLY_API_KEY is undefined at step 3:
# → fetch() sends "Authorization: Bearer undefined"
# → API returns 401 Unauthorized
# → Build might "succeed" but pages have errors baked in
```

### Pages Router (Legacy) Example

```typescript
// pages/blog/[slug].tsx - Pages Router

export async function getStaticProps({ params }) {
  // THIS RUNS AT BUILD TIME TOO!
  const response = await fetch(
    `${process.env.STRAPI_URL}/api/blogs/${params.slug}`,
    {
      headers: {
        Authorization: `Bearer ${process.env.STRAPI_API_TOKEN}`, // Must exist NOW
      },
    }
  )

  const blog = await response.json()

  return {
    props: { blog },
    revalidate: 3600, // ISR: rebuild every hour
  }
}
```

## Step 1: Local Development Analysis

### Why It Works Locally

```bash
# What developers do (consciously or unconsciously):

# 1. Create .env.local ONCE (persists across sessions)
$ cat > apps/ui/.env.local << EOF
STRAPI_REST_READONLY_API_KEY=my-local-token
NEXT_PUBLIC_STRAPI_URL=http://localhost:1337
EOF

# 2. Build (variables already present)
$ yarn build
# ✅ process.env.STRAPI_REST_READONLY_API_KEY = "my-local-token"

# 3. Start server
$ yarn start
# ✅ SSR routes work because build succeeded
```

**Key insight:** `.env.local` is a **persistent file** on your machine. It exists before every build.

## Step 2: CI Environment Difference

### Why It Fails in CI

```yaml
# .github/workflows/ci.yml - WRONG ORDER

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4
        # No .env.local in repo (gitignored)

      - name: Install dependencies
        run: yarn install --frozen-lockfile

      - name: Build UI # ❌ RUNS WITHOUT ENV VARS
        run: yarn workspace @repo/ui build
        # process.env.STRAPI_REST_READONLY_API_KEY = undefined
        # SSR routes fail to fetch data
        # Build completes with error pages

      - name: Set Environment Variables # TOO LATE!
        run: |
          echo "STRAPI_REST_READONLY_API_KEY=${{ secrets.API_TOKEN }}" >> apps/ui/.env.local
        # .env.local created AFTER build
        # Variables now available but build already done with broken pages

      - name: Run E2E Tests
        run: yarn test:e2e
        # Tests fail - pages were built incorrectly
```

### The Flow Breakdown

```
WRONG CI FLOW:
┌─────────────────────┐
│ Checkout code       │ (no .env.local)
├─────────────────────┤
│ Install deps        │
├─────────────────────┤
│ Build UI            │ ← SSR routes execute with undefined vars ❌
│ (process.env = {})  │    Build "succeeds" but pages broken
├─────────────────────┤
│ Set env vars        │ ← .env.local created (too late!)
│ (.env.local created)│
├─────────────────────┤
│ Run tests           │ ← Tests fail (pages built incorrectly)
└─────────────────────┘

LOCAL DEV FLOW (WHY IT WORKS):
┌─────────────────────┐
│ .env.local exists   │ ← Created days/weeks ago, persists
├─────────────────────┤
│ Build UI            │ ← SSR routes execute with vars present ✅
│ (process.env = {...})│   Build succeeds with correct pages
├─────────────────────┤
│ Run tests           │ ← Tests pass (pages built correctly)
└─────────────────────┘
```

## Step 3: The Correct Workflow Order

### ✅ Fixed GitHub Actions Workflow

```yaml
# .github/workflows/ci.yml - CORRECT ORDER

name: CI

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

env:
  # Set at job level for visibility
  STRAPI_REST_READONLY_API_KEY: ${{ secrets.STRAPI_API_TOKEN }}

jobs:
  test:
    runs-on: ubuntu-latest

    services:
      postgres:
        image: postgres:16-alpine
        env:
          POSTGRES_PASSWORD: postgres
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: "20"
          cache: "yarn"

      - name: Install dependencies
        run: yarn install --frozen-lockfile

      # ============================================================
      # CRITICAL: Set environment variables BEFORE build
      # ============================================================
      - name: Prepare Environment Variables
        run: |
          # Copy example files
          cp apps/strapi/.env.example apps/strapi/.env
          cp apps/ui/.env.local.example apps/ui/.env.local

          # Add secrets (must happen BEFORE build!)
          echo "STRAPI_REST_READONLY_API_KEY=${{ env.STRAPI_REST_READONLY_API_KEY }}" >> apps/ui/.env.local
          echo "NEXT_PUBLIC_STRAPI_URL=http://localhost:1337" >> apps/ui/.env.local
          echo "NODE_ENV=production" >> apps/ui/.env.local

      - name: Verify Environment (Debug Step)
        run: |
          echo "✅ Checking .env.local contents..."
          cat apps/ui/.env.local
          echo "---"
          grep -q "STRAPI_REST_READONLY_API_KEY" apps/ui/.env.local && echo "✅ Token present in .env.local"

      # Now build has access to environment variables
      - name: Build UI
        run: yarn workspace @repo/ui build
        env:
          NODE_ENV: production
        # During build:
        # - .env.local already exists ✅
        # - process.env.STRAPI_REST_READONLY_API_KEY has value ✅
        # - SSR routes fetch data successfully ✅

      - name: Start Strapi
        run: |
          yarn workspace @repo/strapi db:seed
          yarn workspace @repo/strapi develop &
        env:
          DATABASE_URL: postgres://postgres:postgres@localhost:5432/strapi_test

      - name: Wait for Strapi
        run: |
          for i in {1..30}; do
            if curl -f http://localhost:1337/admin; then
              echo "✅ Strapi ready"
              exit 0
            fi
            echo "⏳ Waiting for Strapi... ($i/30)"
            sleep 2
          done
          exit 1

      - name: Run E2E Tests
        run: yarn test:e2e
        # Tests pass - pages built correctly with proper authentication
```

## Common Pitfalls & Solutions

### ❌ Pitfall 1: "Environment Variables are Runtime-Only"

**Wrong assumption:**

> "Environment variables are for the running server, not the build process."

**Reality:**

> SSR frameworks execute server-side code during build to pre-render pages.

**Solution:** Always set env vars before build step.

---

### ❌ Pitfall 2: Using NEXT_PUBLIC for Server Secrets

**Problem:**

```typescript
// ❌ WRONG: Exposing server secret to client
const token = process.env.NEXT_PUBLIC_STRAPI_API_TOKEN
```

**Why it's wrong:**

- `NEXT_PUBLIC_*` variables are embedded in client-side JavaScript
- Anyone can view them in browser DevTools
- Security vulnerability for API tokens, database credentials

**Solution:**

```typescript
// ✅ CORRECT: Server-only variable
const token = process.env.STRAPI_REST_READONLY_API_KEY
// Available in server components, API routes, getStaticProps
// NOT exposed to client-side code
```

---

### ❌ Pitfall 3: Not Matching Local Dev Workflow

**Problem:**

```yaml
# CI does this:
- build (no vars)
- set vars (too late)

# Local dev does this:
- set vars (.env.local exists)
- build (has vars)
# Mismatch = "works locally, fails in CI"
```

**Solution:** CI should mirror local development workflow exactly.

---

### ❌ Pitfall 4: Setting Env Vars in Wrong Step

**Problem:**

```yaml
- name: Build UI
  run: yarn build
  env:
    STRAPI_API_TOKEN: ${{ secrets.TOKEN }}
  # Variables available in shell, but Next.js reads from .env.local
```

**Solution:**

```yaml
- name: Set Environment Variables
  run: echo "STRAPI_API_TOKEN=${{ secrets.TOKEN }}" >> apps/ui/.env.local

- name: Build UI
  run: yarn build
  # Next.js reads from .env.local (written in previous step)
```

## Decision Framework

**When to set environment variables:**

| Scenario                                | Set Before Build? | Reasoning                                       |
| --------------------------------------- | ----------------- | ----------------------------------------------- |
| **SSR data fetching**                   | ✅ Yes            | Build-time pre-rendering needs API access       |
| **Build-time feature flags**            | ✅ Yes            | Code splitting decisions during build           |
| **API endpoints for static generation** | ✅ Yes            | getStaticProps/fetch runs during build          |
| **Client-side only (NEXT*PUBLIC*\*)**   | ⚠️ Either         | Embedded during build, but no API calls         |
| **Runtime-only API calls**              | ⚠️ Either         | No build dependency, but consistency helps      |
| **Production secrets (database)**       | ✅ Yes            | Seed scripts or migrations may run before build |

**Rule of thumb:** When in doubt, set before build. It matches local development and prevents undefined errors.
