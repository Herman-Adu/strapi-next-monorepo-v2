## The Problem: Why Fixed Sleep Timers Fail

### Typical Flawed Approach

```javascript
// ❌ BAD: Fixed sleep timer approach
async function startServices() {
  await startDatabase()
  await sleep(30000) // Hope 30 seconds is enough?
  await startAPI()
  await sleep(20000) // Hope 20 seconds is enough?
  await startFrontend()
}

function sleep(ms) {
  return new Promise((resolve) => setTimeout(resolve, ms))
}
```

### Problems with This Approach

| Issue                        | Impact                                          | Example                                                  |
| ---------------------------- | ----------------------------------------------- | -------------------------------------------------------- |
| **Fast machines waste time** | Developer waiting 50s when service ready in 10s | MacBook Pro M3: PostgreSQL ready in 3s, waits 30s anyway |
| **Slow machines fail**       | Services need >50s on older hardware            | GitHub Actions: Strapi takes 60s, times out at 50s       |
| **No feedback**              | Can't tell if stuck or loading                  | Staring at terminal, wondering if it crashed             |
| **Different environments**   | What works locally fails in CI                  | Local: 15s, CI: 35s (different hardware)                 |

### Real Example from Our Codebase

**Before health checks:**

- Development startup: 90-120 seconds (manual coordination)
- Error rate: 20% (Strapi not ready when frontend starts)
- 3 terminal windows required
- 6-8 manual steps per startup

**After health checks:**

- Development startup: 15 seconds (automated)
- Error rate: 0% (adaptive polling)
- 1 terminal window
- 1 command: `yarn dev`

## Step 1: Create HTTP Health Check Function

First, let's build a function that checks if a service is actually ready (not just if the port is listening).

### Implementation

```javascript
// health-check.js
const http = require("http")

/**
 * Check if an HTTP service is healthy and ready
 * @param {string} url - Full URL to health check endpoint
 * @param {number} timeout - Request timeout in milliseconds
 * @returns {Promise<boolean>} - true if service ready, false otherwise
 */
async function checkServiceHealth(url, timeout = 1000) {
  return new Promise((resolve) => {
    const request = http.get(url, { timeout }, (response) => {
      // 200 OK or 302 Redirect = service ready
      // (some services redirect /health to /admin)
      resolve(response.statusCode === 200 || response.statusCode === 302)
    })

    // Connection refused = service not started yet
    request.on("error", () => resolve(false))

    // Timeout = service slow or hung
    request.on("timeout", () => {
      request.destroy()
      resolve(false)
    })
  })
}

module.exports = { checkServiceHealth }
```

### Why This Works

1. **HTTP-level check:** Tests if application is ready, not just if port is open
2. **Timeout protection:** Won't hang forever if service crashed
3. **Error handling:** Gracefully handles connection refused (service not started)
4. **Status code flexibility:** Accepts 200 OK or 302 Redirect (covers more scenarios)

### Test It

```javascript

  // Test against a running service
  const isReady = await checkServiceHealth("http://localhost:1337/admin")

}

test()
```

## Step 2: Add Polling Loop with Progress Logging

Now wrap the health check in a polling loop that retries until the service is ready.

### Implementation

```javascript
// wait-for-service.js
const { checkServiceHealth } = require("./health-check")

/**
 * Wait for a service to be ready via HTTP polling
 * @param {string} serviceName - Human-readable service name for logs
 * @param {string} url - Health check endpoint URL
 * @param {number} maxAttempts - Maximum polling attempts (default 60)
 * @param {number} interval - Milliseconds between attempts (default 2000)
 * @returns {Promise<void>} - Resolves when ready, rejects on timeout
 */
async function waitForService(
  serviceName,
  url,
  maxAttempts = 60,
  interval = 2000
) {
  console.log(`⏳ Waiting for ${serviceName} to be ready...`)

  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    const isReady = await checkServiceHealth(url)

    if (isReady) {
      const elapsedSeconds = (attempt * interval) / 1000
      console.log(`✅ ${serviceName} ready after ${elapsedSeconds}s`)
      return
    }

    // Log progress every 5 attempts (every 10 seconds with 2s interval)
    if (attempt % 5 === 0) {
      console.log(`   Still waiting... (${attempt}/${maxAttempts} attempts)`)
    }

    // Wait before next attempt
    await new Promise((resolve) => setTimeout(resolve, interval))
  }

  // Max attempts exceeded
  const timeoutSeconds = (maxAttempts * interval) / 1000
  throw new Error(
    `❌ ${serviceName} failed to start after ${timeoutSeconds}s (${maxAttempts} attempts)`
  )
}

module.exports = { waitForService }
```

### Configuration Tuning

| Parameter         | Default   | Fast Machines | Slow Machines | CI Environments |
| ----------------- | --------- | ------------- | ------------- | --------------- |
| `maxAttempts`     | 60        | 30 (1 min)    | 90 (3 min)    | 120 (4 min)     |
| `interval`        | 2000ms    | 1000ms        | 2000ms        | 2000ms          |
| **Total timeout** | **2 min** | **30s**       | **3 min**     | **4 min**       |

### Why These Defaults?

- **60 attempts × 2s = 2 minutes:** Enough for most services, even on slow hardware
- **2-second interval:** Not too aggressive (spam), not too slow (user waiting)
- **Log every 5 attempts (10s):** User sees progress without console spam

## Step 3: Use in Development Orchestration Script

Put it all together in a complete orchestration script.

### Full Example

```javascript
// dev-orchestrated.js
const { spawn } = require("child_process")
const { waitForService } = require("./wait-for-service")

// Color codes for pretty terminal output
const colors = {
  reset: "\x1b[0m",
  cyan: "\x1b[36m",
  green: "\x1b[32m",
  yellow: "\x1b[33m",
  red: "\x1b[31m",
}

function log(message, color = colors.reset) {
  console.log(`${color}${message}${colors.reset}`)
}

// Start PostgreSQL via Docker Compose
function startDatabase() {
  return new Promise((resolve, reject) => {
    log("🐘 Starting PostgreSQL...", colors.cyan)

    const db = spawn("docker", ["compose", "up", "-d", "db"], {
      shell: true,
      stdio: "inherit",
    })

    db.on("close", (code) => {
      if (code === 0) {
        // Wait 3 seconds for PostgreSQL to initialize
        setTimeout(() => resolve(), 3000)
      } else {
        reject(new Error(`PostgreSQL failed to start (exit code ${code})`))
      }
    })
  })
}

// Start Strapi backend
function startStrapi() {
  return new Promise((resolve) => {
    log("🚀 Starting Strapi backend...", colors.cyan)

    const strapi = spawn(
      "yarn",
      ["workspace", "@repo/strapi", "run", "develop"],
      {
        shell: true,
        stdio: ["ignore", "pipe", "pipe"],
      }
    )

    // Forward output with prefix
    strapi.stdout.on("data", (data) => {
      process.stdout.write(`${colors.cyan}[Strapi]${colors.reset} ${data}`)
    })

    // Return process handle after 2s
    setTimeout(() => resolve(strapi), 2000)
  })
}

// Start Next.js UI
function startUI() {
  log("⚛️  Starting Next.js UI...", colors.green)

  const ui = spawn("yarn", ["workspace", "@repo/ui", "run", "dev"], {
    shell: true,
    stdio: "inherit",
  })

  return ui
}

// Main orchestration flow
async function main() {
  let strapiProcess, uiProcess

  try {
    log("\n" + "=".repeat(60), colors.yellow)
    log("🎯 Development Environment Orchestrator", colors.yellow)
    log("=".repeat(60) + "\n", colors.yellow)

    // Step 1: Start database
    await startDatabase()

    // Step 2: Start Strapi
    strapiProcess = await startStrapi()

    // Step 3: Wait for Strapi to be READY (not just started!)
    await waitForService("Strapi", "http://localhost:1337/admin")

    // Step 4: Start UI (safe now because Strapi is ready)
    uiProcess = startUI()

    log("\n" + "=".repeat(60), colors.green)
    log("✅ All services started successfully!", colors.green)
    log("=".repeat(60) + "\n", colors.green)
    log("📍 Strapi Admin: http://localhost:1337/admin", colors.cyan)
    log("📍 Next.js UI:   http://localhost:3000", colors.cyan)
    log("\n💡 Press Ctrl+C to stop all services\n", colors.yellow)

    // Graceful shutdown
    const cleanup = () => {
      log("\n🛑 Shutting down services...", colors.yellow)
      if (strapiProcess && !strapiProcess.killed) {
        strapiProcess.kill("SIGTERM")
      }
      if (uiProcess && !uiProcess.killed) {
        uiProcess.kill("SIGTERM")
      }
      process.exit(0)
    }

    process.on("SIGINT", cleanup) // Ctrl+C
    process.on("SIGTERM", cleanup) // Kill command
  } catch (error) {
    log(`\n❌ Error: ${error.message}`, colors.red)
    process.exit(1)
  }
}

main()
```

### Add to package.json

```json
{
  "scripts": {
    "dev": "node scripts/dev-orchestrated.js"
  }
}
```

## Common Pitfalls & Solutions

### ❌ Pitfall 1: Using TCP Socket Checks Instead of HTTP

**Problem:**

```javascript
// Port is listening, but application not ready
const net = require("net")
const socket = net.connect(1337, "localhost")
socket.on("connect", () => {
  console.log("Port open!") // But Strapi might still be building...
})
```

**Why it fails:** Port listens before application fully initializes.

**✅ Solution:** Use HTTP health check (tests application-level readiness).

---

### ❌ Pitfall 2: No Timeout on HTTP Requests

**Problem:**

```javascript
const response = await fetch(url) // Can hang forever if service dead
```

**✅ Solution:** Always set timeout:

```javascript
const response = await fetch(url, { timeout: 1000 })
```

---

### ❌ Pitfall 3: Too Aggressive Polling

**Problem:**

```javascript
await waitForService("API", url, 120, 100) // Check every 100ms
// Spams logs, wastes CPU, no meaningful benefit
```

**✅ Solution:** 1-2 second intervals are optimal for most services.

---

### ❌ Pitfall 4: Too Few Max Attempts

**Problem:**

```javascript
await waitForService("Strapi", url, 10, 2000) // Only 20 seconds total
// Fails on slow machines or CI
```

**✅ Solution:** Allow 2-4 minutes for most services (60-120 attempts × 2s).
