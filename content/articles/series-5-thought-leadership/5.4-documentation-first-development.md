## The Moment Everything Changed

**December 2024:** I spent 6 hours debugging why a component wasn't rendering.

**Root cause:** I forgot the component required a specific prop structure I had designed 2 months earlier.

**Cost:** 6 hours (vs 30 seconds if I had written docs)

**That day, I committed to documentation-first development.**

---

## What Is Documentation-First Development?

**Traditional workflow:**

1. Write code
2. Test code
3. (Maybe) write docs
4. Ship
5. Forget how it works
6. Debug later (expensive)

**Documentation-first workflow:**

1. **Write docs first** (explains what you're building)
2. Code (implementation is easier with clear plan)
3. Test (docs define test cases)
4. Ship
5. Return 6 months later (docs refresh memory instantly)

**Key difference:** Documentation is the design phase, not an afterthought.

## Real Example: Adding a New Section Component

### Traditional Approach (No Docs)

**Day 1:**

```typescript
// apps/ui/src/components/FeatureSection.tsx
export function FeatureSection({ data }: { data: any }) {
  return (
    <div>
      {/* Start coding without clear plan */}
      {data.items?.map(item => (
        <div key={item.id}>
          {item.title}
          {/* Wait, should this be item.heading? */}
        </div>
      ))}
    </div>
  )
}
```

**Problems encountered:**

- Unclear prop structure (guessing field names)
- Forgot about edge cases (what if `items` is empty?)
- No TypeScript types defined
- Unclear Strapi schema requirements
- 2 hours wasted on trial and error

---

### Documentation-First Approach

**Step 1: Write component documentation (15 minutes)**

````markdown
# Feature Section Component

## Purpose

Display 2-4 features with icon, title, description in responsive grid.

## Strapi Schema

- `badge` (component) - Optional badge above title
- `header` (component) - Title + subtitle
- `items` (component, repeatable) - Feature cards
  - `icon` (string) - Lucide icon name
  - `title` (string, required)
  - `description` (richtext)
- `background` (enumeration) - white, gray, primary

## Props

```typescript
interface FeatureSectionProps {
  badge?: Badge
  header: SectionHeader
  items: FeatureItem[] // Must have 2-4 items
  background: Background
}
```
````

## Edge Cases

- If items.length < 2 → Show warning in Strapi
- If items.length > 4 → Grid wraps to new row
- If no header → Show items only

## Responsive Behavior

- Mobile: 1 column
- Tablet: 2 columns
- Desktop: 2-4 columns (based on items.length)

## Related Components

- Uses `SectionWrapper` for background
- Uses `SectionBadge` for badge
- Uses `SectionHeader` for header

````

**Step 2: Code implementation (30 minutes)**

```typescript
// Now implementation is straightforward because plan is clear
export function FeatureSection({ badge, header, items, background }: FeatureSectionProps) {
  if (items.length < 2 || items.length > 4) {
    console.warn('FeatureSection should have 2-4 items')
  }

  return (
    <SectionWrapper background={background}>
      {badge && <SectionBadge badge={badge} />}
      {header && <SectionHeader header={header} />}
      <div className={`grid grid-cols-1 md:grid-cols-2 ${items.length > 2 ? 'lg:grid-cols-4' : ''}`}>
        {items.map(item => (
          <FeatureCard key={item.id} item={item} />
        ))}
      </div>
    </SectionWrapper>
  )
}
````

**Result:** 45 minutes total (vs 2+ hours trial-and-error)

**Bonus:** Documentation already done when feature ships.

## The 5 Core Principles

### 1. Documentation Is the Design Phase

**Instead of:** "Let me code and see what happens"  
**Do this:** "Let me document what I want to build"

**Why it works:**

- Writing forces clarity (can't document what you don't understand)
- Reveals edge cases before coding (cheaper to fix)
- Creates shared understanding (team alignment)
- Defines success criteria (what does "done" mean?)

**Example:**

Before writing a complex data transformation function, I document:

````markdown
# transformStrapiResponse

## Purpose

Convert Strapi API response to typed frontend data structure.

## Input

```json
{
  "data": {
    "id": 1,
    "attributes": {
      "title": "Page Title",
      "sections": [...]
    }
  },
  "meta": { "pagination": {...} }
}
```
````

## Output

```typescript
{
  id: number
  title: string
  sections: Section[]
}
```

## Transformations

1. Flatten `data.attributes` → root level
2. Convert `sections` array using `transformSection()`
3. Remove `meta` (not needed in frontend)

## Edge Cases

- If `data` is null → return null
- If `sections` is empty → return empty array
- If required field missing → throw error

```

**Result:** Function writes itself because behavior is fully specified.

**Bad:** Separate wiki/Confluence that gets outdated
**Good:** Markdown files in `docs/` folder alongside code

**My structure:**

```

├── docs/
│ ├── 01-getting-started/

**Benefits:**

- ✅ Docs versioned with code (Git history)
- ✅ Docs reviewed in PRs (quality control)
- ✅ Searchable with `grep` (no separate search tool)
- ✅ Easy to link (relative paths)
- ✅ Always in sync (or CI fails)

### 3. Document the "Why," Not Just the "What"

**Bad documentation:**

```markdown
# API Configuration

Set `API_URL` in `.env` file.
````

**Good documentation:**

````markdown
# API Configuration

## What

Set `API_URL` environment variable to your Strapi backend URL.

## Why

Next.js needs to know where to fetch content. Using env var allows:

- Different URLs per environment (dev, staging, prod)
- No hardcoded URLs in code (easier to change)
- Security (can hide real API URL from client)

## How

```bash
# .env.local
API_URL=http://localhost:1337
```
````

## Common Issues

- **Error: "fetch failed"** → Check API_URL is correct
- **Error: "CORS"** → Strapi CORS settings need update
- **404 errors** → Check Strapi is running on specified port

````

**Result:** Developer understands context, not just commands.

### 4. Examples Over Explanations

**Principle:** Show don't tell.

**Bad:**

```markdown
The SectionWrapper component accepts background, children, and optional className props for styling flexibility.
````

**Good:**

````markdown
## SectionWrapper Component

### Basic Usage

```tsx
<SectionWrapper background="white">
  <h2>Content Here</h2>
</SectionWrapper>
```
````

### With Primary Background

```tsx
<SectionWrapper background="primary">
  <h2>Hero Section</h2>
</SectionWrapper>
```

### With Custom Styles

```tsx
<SectionWrapper background="gray" className="py-32">
  <h2>Extra Padding</h2>
</SectionWrapper>
```

````

**Why examples work:**

- Faster to understand (visual learning)
- Copy-paste ready (productivity)
- Shows common patterns (best practices)
- Reveals edge cases (what's possible?)

### 5. Docs Are Living Documents

**Documentation rots fast.** Combat this with:

#### Regular Reviews

```markdown
<!-- At top of each doc -->
**Last Reviewed:** December 10, 2025
**Status:** ✅ Current | ⚠️ Needs Update | ❌ Deprecated
````

#### Change Logs

```markdown
## Changelog

### 2025-12-10

- Added grid layout support
- Deprecated `columns` prop (use `gridColumns` instead)

### 2025-11-15

- Initial documentation
```

#### Automated Checks

```yaml
# .github/workflows/docs-check.yml
name: Documentation Check
on: [pull_request]
jobs:
  check-links:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Check dead links
        run: npx markdown-link-check docs/**/*.md
```

### 2. Architecture Decision Records (ADRs)

**Purpose:** Document why you made key decisions.

**Template:**

```markdown
# ADR-001: Use Strapi Instead of Custom CMS

## Status
Accepted (December 2024)

## Context
Need headless CMS for content management. Options:
- Build custom (400+ hours)
- Contentful (expensive, lock-in)
- Strapi (open source, flexible)

## Decision
Use Strapi v5.

## Consequences
### Positive
- 400+ hours saved vs custom build
- No vendor lock-in (self-hosted)
- Active community, plugins available
- TypeScript type generation

### Negative
- 20 hours learning curve
- Need to maintain updates
- Admin UI not fully customizable

## Revisit Conditions
- If we need >50K content entries (Strapi scale limits)
- If we need white-label admin UI
- If Strapi gets acquired/abandoned
````

**When to write ADRs:**

- Choosing tech stack (framework, database, hosting)
- Major architecture changes (monorepo, folder structure)
- Process changes (CI/CD, testing strategy)

### 5. Troubleshooting Guides

**Document every bug that took >1 hour to fix:**

```markdown
# Common Issues

## "Password authentication failed for user strapi_user"

### Symptoms
- Strapi won't start
- PostgreSQL connection error
- Error code: 28P01

### Root Cause
PostgreSQL 17 changed default auth from MD5 to SCRAM-SHA-256.
Strapi user still configured for MD5.

### Solution
Edit `pg_hba.conf`:
````

# Change this line:

local all all scram-sha-256

# To this:

local all all md5

````

Restart PostgreSQL:
```bash
# macOS
brew services restart postgresql

# Linux
sudo systemctl restart postgresql
````

### Prevention

Use SCRAM-SHA-256 from the start (recreate user with new method).

### Related Articles

- Tutorial 3.1: PostgreSQL Authentication Setup

````

## How to Start Documentation-First

### Week 1: Document Existing Project

1. **Create docs structure**
   ```bash
   mkdir -p docs/{01-getting-started,02-architecture,03-components}
````

2. **Write README.md** (1 hour)

   - Project description
   - Tech stack
   - Quick start
   - Link to detailed docs

3. **Document 3 most-used components** (3 hours)

   - Purpose, props, usage examples
   - Strapi integration
   - Related components

4. **Write troubleshooting guide** (1 hour)
   - List 5 common errors you've debugged
   - Symptoms, root cause, solution

**Total:** 5 hours upfront investment

---

### Week 2: Adopt Documentation-First Workflow

**New feature workflow:**

1. **Before coding:** Write doc (15-30 min)
   - Purpose, API, edge cases, examples
2. **Code implementation** (faster with clear plan)

3. **Update doc if reality differs** (5 min)

4. **PR includes doc changes** (review together)

**Example commit:**

```
feat: Add team member section component

- Implements FeatureSection with 2-4 item grid
- Strapi schema supports badge, header, items
- Responsive: 1 col mobile, 2 col tablet, 4 col desktop
- Documentation: docs/04-components/team-section.md
```

---

### Week 3: Automate Doc Maintenance

**Set up automated checks:**

```yaml
# .github/workflows/docs.yml
name: Documentation CI
on: [pull_request]
jobs:
  check-links:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Check markdown links
        run: npx markdown-link-check docs/**/*.md

      - name: Check for outdated docs
        run: |
          # Fail if docs haven't been updated in 6+ months
          find docs -name "*.md" -mtime +180 -exec echo "Outdated: {}" \;
```

## Common Mistakes

### Mistake 1: Writing Docs After Code

**Symptom:** Docs always out of date, treated as chore

**Fix:** Write docs first (design phase), then code.

---

### Mistake 2: Separate Wiki/Confluence

**Symptom:** Docs not versioned, link rot, access issues

**Fix:** Markdown in `docs/` folder, committed with code.

---

### Mistake 3: No Examples

**Symptom:** Docs are theoretical, developers still confused

**Fix:** Every feature needs 2-3 code examples.

---

### Mistake 4: Never Updating

**Symptom:** Old docs worse than no docs (misleading)

**Fix:** Review docs every 3-6 months, mark outdated sections.

---

## Key Takeaways

✅ **Write docs before code** (design phase, not afterthought)  
✅ **Docs live with code** (Markdown in Git, not separate wiki)  
✅ **Document "why"** (context matters, not just commands)  
✅ **Examples over theory** (show don't tell)  
✅ **Docs are living** (review every 3-6 months)  
✅ **ROI is massive** (18.5 hours/month saved = $22K/year)  
✅ **Start small** (README + 3 components = 5 hours)

**Bottom line:** Documentation-first development makes coding faster, not slower.

## Next Steps

**If you're starting from scratch:**

1. Create `docs/` folder structure
2. Write comprehensive README.md (1 hour)
3. Document your 3 most complex components (3 hours)
4. Add 1 ADR explaining a key decision (30 min)
5. Commit to documenting before your next feature

**If you have undocumented code:**

1. Start with troubleshooting guide (capture knowledge)
2. Document 1 component per week
3. Don't try to document everything at once
4. Focus on high-impact areas (onboarding, common bugs)
