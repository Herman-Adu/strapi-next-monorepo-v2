## The Decision That Changed Everything

**Before monorepo (3 separate repos):**

- **Strapi backend** → `git@github.com:user/project-backend.git`
- **Next.js frontend** → `git@github.com:user/project-frontend.git`
- **Shared types** → Copy-paste or npm package hell

**Problems:**

- 3 separate `git clone` commands for onboarding
- TypeScript types out of sync (copy-paste errors)
- 3 separate CI/CD pipelines to maintain
- Version management nightmare (`v1.2.3-backend` vs `v1.2.4-frontend`?)
- Atomic commits impossible (change API + frontend = 2 PRs, 2 reviews, coordination hell)

**Monthly time waste:** ~40 hours (type syncing, version coordination, CI duplication)

---

**After monorepo (1 unified repo):**

```
strapi-next-monorepo-v2/
├── apps/
│   ├── strapi/     # Backend
│   └── ui/         # Frontend
└── packages/
    └── shared-data/  # Shared TypeScript types
```

**What changed:**

✅ Single `git clone` for full project  
✅ Shared types (import from `@repo/shared-data`)  
✅ One CI/CD pipeline (with smart caching)  
✅ One version number (`v2.1.0` covers everything)  
✅ Atomic commits (backend + frontend changes in one PR)

**Time saved:** 40 hours/month → 2 hours/month

**This article explains when monorepos win, when they don't, and how to decide.**

## Monorepo vs Polyrepo: Quick Definitions

### Monorepo (Single Repository)

**All projects in one Git repository.**

```
my-monorepo/
├── apps/
│   ├── mobile-app/
│   ├── web-app/
│   └── admin-dashboard/
├── packages/
│   ├── ui-components/
│   ├── shared-utils/
│   └── api-client/
└── package.json  # Root orchestrator
```

**Examples in the wild:**

- Google (1 repo, 1 billion+ files)
- Facebook/Meta (1 repo)
- Microsoft (migrated to monorepo)
- Twitter, Uber, Airbnb

---

### Polyrepo (Multiple Repositories)

**Each project in separate Git repository.**

```
my-projects/
├── mobile-app/           # git@github.com:user/mobile-app.git
├── web-app/              # git@github.com:user/web-app.git
├── admin-dashboard/      # git@github.com:user/admin-dashboard.git
├── ui-components/        # git@github.com:user/ui-components.git (npm package)
├── shared-utils/         # git@github.com:user/shared-utils.git (npm package)
└── api-client/           # git@github.com:user/api-client.git (npm package)
```

**Examples in the wild:**

- Linux kernel (polyrepo of subsystems)
- AWS (hundreds of separate services)
- Most small startups

## The Decision Framework

### When to Use Monorepo ✅

#### 1. Tightly Coupled Projects

**You have monorepo if:**

- Changes often span multiple projects  
  Example: API change requires frontend update
- Shared code is frequent  
  Example: TypeScript types, UI components, utilities
- Versioning needs coordination  
  Example: Backend v2.0 breaks frontend v1.x

**Real Example (My Project):**

| Change Type         | Repos Touched              | Monorepo Benefit |
| ------------------- | -------------------------- | ---------------- |
| Add CMS field       | Backend + Frontend + Types | 1 commit, 1 PR   |
| Update API response | Backend + Types + Frontend | Atomic change    |
| Shared component    | Package + Both apps        | Import locally   |
| CI/CD improvement   | All projects               | Update once      |

**Polyrepo equivalent:** 3-6 PRs, version coordination, integration testing delays.

---

#### 2. Small Team (<10 People)

**Monorepo advantages:**

- **Single source of truth** - Everyone sees everything
- **No access control needed** - Team trusts each other
- **Simplified onboarding** - One `git clone`, one README
- **Code reviews easier** - Reviewers see full context

**Team size sweet spot:** 1-10 people

**Why?** Beyond 10 people, clone times increase, CI slows, permission boundaries needed.

---

#### 3. Shared Tooling

**You benefit if:**

- Same linting rules (ESLint, Prettier)
- Same TypeScript config (strict mode, target ES2022)
- Same testing framework (Playwright, Vitest)
- Same CI/CD patterns (GitHub Actions workflows)

**Monorepo structure:**

```
packages/
├── eslint-config/       # Shared ESLint rules
├── typescript-config/   # Shared tsconfig.json
├── prettier-config/     # Shared Prettier settings
└── jest-config/         # Shared test config
```

**Usage in apps:**

```json
// apps/strapi/package.json
{
  "eslintConfig": {
    "extends": ["@repo/eslint-config"]
  },
  "prettier": "@repo/prettier-config"
}
```

**Benefit:** Update linting rules once → applies everywhere.

---

#### 4. Fast Iteration Required

**Monorepo speeds up:**

- **Atomic commits** - Backend + frontend change in one commit
- **Single PR** - Review both sides together
- **No version coordination** - Everything in sync by default
- **Instant code sharing** - No npm publish/install cycle

**Real Example:**

**Polyrepo workflow (Strapi field change):**

1. Update backend API (30 min)
2. Commit, push, PR 1
3. Wait for review/approval (2 hours)
4. Merge backend PR
5. Publish types package to npm (10 min)
6. Update frontend dependencies (5 min)
7. Update frontend code (20 min)
8. Commit, push, PR 2
9. Wait for review/approval (1 hour)
10. Merge frontend PR

**Total:** ~4 hours (with coordination overhead)

**Monorepo workflow:**

1. Update backend API (30 min)
2. Update shared types (5 min)
3. Update frontend code (20 min)
4. Commit, push, single PR (includes all changes)
5. Wait for review (30 min)
6. Merge

**Total:** ~1.5 hours (60% time saved)

---

### When to Use Polyrepo 🔀

#### 1. Independent Release Cycles

**You have polyrepo if:**

- Projects deploy independently  
  Example: Mobile app (App Store) vs web app (continuous deployment)
- Different versioning schemes  
  Example: `v2.1.0-web` vs `v1.5.0-mobile`
- Different stakeholders own different projects  
  Example: Team A owns backend, Team B owns mobile, Team C owns admin

**Example: E-commerce Platform**

```
├── customer-web-app/       # Deploy 50x/day
├── seller-dashboard/       # Deploy 10x/day
├── mobile-ios/             # Deploy 1x/month (App Store review)
├── mobile-android/         # Deploy 2x/month (Play Store)
└── backend-api/            # Deploy 20x/day
```

**Why polyrepo:** Each has different release cadence, independent deploy pipelines.

---

#### 2. Large Organization (50+ People)

**Polyrepo advantages at scale:**

- **Access control** - Restrict who can see/edit what
- **Clone speed** - Small repos clone faster than giant monorepo
- **CI performance** - Only test changed repo, not everything
- **Ownership boundaries** - Clear team responsibilities

**Enterprise example:**

| Team         | Repo          | Access                     |
| ------------ | ------------- | -------------------------- |
| **Platform** | `backend-api` | Full access                |
| **Web**      | `web-app`     | Read backend, write web    |
| **Mobile**   | `mobile-app`  | Read backend, write mobile |
| **Security** | All repos     | Audit access only          |

**Why polyrepo:** Access control + organizational boundaries.

---

#### 3. Public Open Source

**Polyrepo makes sense for:**

- **npm packages** - Each package = separate repo (easy to publish)
- **Focused contributions** - Contributors only clone what they need
- **Star metrics** - Each repo gets own GitHub stars/forks
- **Discovery** - Easier to find individual packages

**Example: Design System**

```
├── design-tokens/        # github.com/user/design-tokens (1.2K stars)
├── react-components/     # github.com/user/react-components (3.5K stars)
├── vue-components/       # github.com/user/vue-components (800 stars)
└── documentation/        # github.com/user/docs (500 stars)
```

**Why polyrepo:** Independent npm packages, separate communities.

---

#### 4. Microservices Architecture

**Polyrepo natural fit:**

- **Independently deployable services**  
  Example: Auth service, payment service, notification service
- **Different tech stacks**  
  Example: Auth (Go), Payment (Python), Notification (Node.js)
- **Service boundaries well-defined**  
  Example: Each service has own database, API, deployment

**Microservices example:**

```
├── auth-service/         # Go, PostgreSQL, Kubernetes
├── payment-service/      # Python, Stripe API, Lambda
├── notification-service/ # Node.js, Redis, SQS
├── user-service/         # Node.js, MongoDB, ECS
└── api-gateway/          # Nginx config repo
```

**Why polyrepo:** Different languages, different deployments, service isolation.

## The Hybrid Approach (Best of Both Worlds)

### Strategy: Monorepo + Polyrepo

**Pattern:**

- **Monorepo for tightly coupled code** (frontend + backend + shared)
- **Polyrepo for independent services** (microservices, external APIs)

**Example structure:**

```
Main Monorepo:
└── core-platform/
    ├── apps/
    │   ├── web-app/
    │   ├── admin-dashboard/
    │   └── mobile-app/
    └── packages/
        ├── ui-components/
        ├── shared-types/
        └── api-client/

Separate Repos:
├── auth-service/         # Independent microservice
├── payment-service/      # Independent microservice
└── ml-recommendation/    # Python ML model (different stack)
```

**Why hybrid:** Fast iteration on core platform, service isolation where needed.

## Real-World Comparison: My Project

### Scenario: Add New CMS Content Type

**Task:** Add "Team Member" content type (name, role, bio, photo)

#### Polyrepo Approach (Before)

**Repos involved:**

1. `strapi-backend` (CMS schema)
2. `shared-types` (TypeScript types)
3. `nextjs-frontend` (component rendering)

**Steps:**

1. **Backend repo:**

   - Add content type schema
   - Commit, push, PR 1
   - Wait for CI (3 min)
   - Review, merge (30 min)

2. **Shared types repo:**

   - Manual type definition
   - Publish to npm (10 min)
   - Version bump (`@company/types@1.2.3`)

3. **Frontend repo:**
   - Update dependencies (`yarn add @company/types@1.2.3`)
   - Add component
   - Commit, push, PR 2
   - Wait for CI (3 min)
   - Review, merge (30 min)

**Total time:** ~2 hours (including coordination, version management, npm publish)

**Failure points:**

- Forgot to update types package → runtime error
- Version mismatch → TypeScript errors
- PR 1 merged but PR 2 not ready → broken deployment

---

#### Monorepo Approach (After)

**Single repo structure:**

```
strapi-next-monorepo-v2/
├── apps/
│   ├── strapi/
│   │   └── src/api/team-member/
│   └── ui/
│       └── src/components/TeamMember.tsx
└── packages/
    └── shared-data/
        └── types/team-member.ts
```

**Steps:**

1. Add Strapi schema (`apps/strapi/src/api/team-member/`)
2. Run type generation script (30 seconds)
3. Types automatically updated in `packages/shared-data/`
4. Build frontend component (imports types from `@repo/shared-data`)
5. Commit, push, single PR (all changes together)
6. CI runs once (tests both backend + frontend)
7. Review, merge

**Total time:** ~45 minutes (60% faster)

**Benefits:**

- ✅ No version coordination
- ✅ No npm publish cycle
- ✅ Types always in sync
- ✅ Atomic commit (backend + types + frontend)
- ✅ Single PR review (full context visible)

## Tooling: How to Build a Monorepo

### Turborepo (Recommended)

**What it is:** High-performance build system for JavaScript/TypeScript monorepos.

**Installation:**

```bash
npx create-turbo@latest
```

**Configuration (`turbo.json`):**

```json
{
  "$schema": "https://turbo.build/schema.json",
  "pipeline": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**", ".next/**"]
    },
    "dev": {
      "cache": false,
      "persistent": true
    },
    "test": {
      "dependsOn": ["build"],
      "outputs": ["coverage/**"]
    }
  }
}
```

**Commands:**

```bash
turbo build    # Build all apps/packages
turbo dev      # Run all dev servers
turbo test     # Run all tests
```

**Caching benefits:**

| Build Type   | Without Turbo | With Turbo | Improvement |
| ------------ | ------------- | ---------- | ----------- |
| Cold build   | 3m 45s        | 2m 40s     | 29% faster  |
| Cached build | 3m 45s        | 15s        | 93% faster  |
| CI build     | 4m 20s        | 1m 10s     | 73% faster  |

---

### Yarn Workspaces (Package Manager)

**Configuration (`package.json`):**

```json
{
  "private": true,
  "workspaces": ["apps/*", "packages/*"]
}
```

**Commands:**

```bash
yarn workspace @repo/strapi add lodash
yarn workspace @repo/ui dev
yarn install  # Installs all workspace dependencies
```

**Benefits:**

- Hoisted dependencies (shared `node_modules`)
- Fast installs (deduplicated packages)
- Local package linking (no npm publish needed)

---

### Alternative Tools

| Tool                | Best For                        | Pros                        | Cons          |
| ------------------- | ------------------------------- | --------------------------- | ------------- |
| **Turborepo**       | JavaScript/TypeScript monorepos | Fast caching, simple config | JS-only       |
| **Nx**              | Large enterprises               | Advanced features, plugins  | Complex setup |
| **Lerna**           | npm packages                    | Publishing workflow         | Slower, older |
| **pnpm workspaces** | Alternative to Yarn             | Faster installs             | Less common   |
| **Rush**            | Microsoft stack                 | Scalable                    | Complex       |

**My choice:** Turborepo + Yarn (simplicity + performance).

## Common Mistakes

### Mistake 1: Monorepo with No Tool

**Symptom:** Manual builds, no caching, slow CI

**Example:**

```bash
# Manual build script (no Turbo)
cd apps/strapi && yarn build
cd ../ui && yarn build
cd ../../packages/shared-data && yarn build
```

**Problem:** No parallelization, no caching, no dependency awareness.

**Fix:** Use Turborepo or Nx.

---

### Mistake 2: Polyrepo with Shared Code

**Symptom:** Copy-paste code, version hell, sync issues

**Example:** Shared TypeScript types copied across 3 repos.

**Problem:** Changes require updating 3 repos manually.

**Fix:** Migrate to monorepo or publish shared code as npm package.

---

### Mistake 3: Giant Monorepo with Everything

**Symptom:** 10GB clone, 20-minute CI, 100+ people

**Example:** All projects + dependencies + build artifacts in Git.

**Problem:** Scale issues, slow dev experience.

**Fix:** Polyrepo for services, monorepo for tightly coupled apps.

---

## Migration Strategies

### Polyrepo → Monorepo

**Steps:**

1. Create new monorepo structure
2. Move repos into `apps/` or `packages/`
3. Set up Turborepo + workspaces
4. Update import paths (`../../shared` → `@repo/shared`)
5. Consolidate CI/CD pipelines
6. Update documentation

**Time:** 1-2 days for small projects

---

### Monorepo → Polyrepo

**Steps:**

1. Identify independent projects
2. Extract into separate repos
3. Publish shared code as npm packages
4. Update import paths (`@repo/shared` → `@company/shared` npm package)
5. Set up separate CI/CD pipelines

**Time:** 2-5 days (depending on coupling)

## Key Takeaways

✅ **Monorepo for tightly coupled projects** (backend + frontend + shared types)  
✅ **Polyrepo for independent services** (microservices, different stacks)  
✅ **Hybrid approach often best** (monorepo core + polyrepo services)  
✅ **Turborepo makes monorepos fast** (caching, parallelization)  
✅ **Team size matters** (1-10 people = monorepo, 50+ = polyrepo)  
✅ **Tooling required** (don't DIY monorepo orchestration)  
✅ **Atomic commits win** (backend + frontend in single PR)

**Bottom line:** Monorepo when projects evolve together. Polyrepo when they deploy independently.

## Next Steps

**If you're starting a new project:**

1. Start with monorepo (easier to split later than merge)
2. Use Turborepo from day 1
3. Set up shared packages early (`@repo/shared-data`, `@repo/eslint-config`)
4. Document workspace commands in README

**If you're stuck in polyrepo hell:**

1. Calculate monthly coordination time waste
2. Estimate 2-day migration cost
3. If waste > migration cost → migrate
4. Start with backend + types + frontend (most coupled)
