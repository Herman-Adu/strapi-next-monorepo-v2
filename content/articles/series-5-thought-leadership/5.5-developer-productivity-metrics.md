# Developer Productivity Metrics That Matter: Stop Tracking Lines of Code

**Reading Time:** 9 minutes

## The Metrics Most Companies Get Wrong

**Bad metric:** Lines of code per week  
**Problem:** Encourages verbose code, discourages refactoring

**Bad metric:** Number of commits  
**Problem:** Encourages tiny commits, meaningless activity

**Bad metric:** Hours worked  
**Problem:** Rewards time, not outcomes

**These metrics optimize for the wrong things.**

---

**What actually matters:**

1. **How fast can you ship?** (Cycle time)
2. **How often do you break things?** (Change failure rate)
3. **How quickly can you fix problems?** (MTTR)
4. **How often do you deploy?** (Deployment frequency)
5. **How does it feel to develop here?** (Developer experience)

**This article covers the 12 metrics I actually track (and why).**

## The 4 DORA Metrics (Industry Standard)

### What Are DORA Metrics?

**DORA** = DevOps Research and Assessment (Google-backed research)

**They identified 4 metrics that predict:**

- Software delivery performance
- Organizational performance
- Team well-being

**Used by:** Google, Netflix, Amazon, Microsoft, Stripe

---

### 1. Deployment Frequency

**Question:** How often do you deploy to production?

**Why it matters:**

- More deploys = smaller changes = less risk
- Fast feedback loop (know if feature works)
- Shipping is a habit (not a scary event)

**Measurement:**

```typescript
deploymentFrequency = totalDeployments / timePeriod

// Example
deploymentFrequency = 140 deploys / 7 days = 20 deploys/day
```

**Benchmarks (Google DORA):**

| Level      | Frequency             | My Project            |
| ---------- | --------------------- | --------------------- |
| **Elite**  | Multiple/day          | ✅ 20/day (on-demand) |
| **High**   | 1/week to 1/month     |                       |
| **Medium** | 1/month to 1/6 months |                       |
| **Low**    | <1/6 months           |                       |

**How to improve:**

- Automate deployment (GitHub Actions, Heroku, Vercel)
- Remove manual approval steps
- Deploy on every merged PR (continuous deployment)
- Make deployments boring (not scary events)

**My setup:**

```yaml
# .github/workflows/deploy.yml
name: Deploy
on:
  push:
    branches: [main]
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Deploy to production
        run: git push heroku main
```

**Result:** Every merge to `main` deploys automatically (no manual intervention).

### 2. Lead Time for Changes

**Question:** How long from code commit to production?

**Why it matters:**

- Fast feedback (did the feature work?)
- Customer value delivered faster
- Smaller batches = easier to debug

**Measurement:**

```typescript
leadTime = deployTime - firstCommitTime

// Example
leadTime = 14:30 - 09:00 = 5.5 hours
```

**Benchmarks:**

| Level      | Lead Time         | My Project                 |
| ---------- | ----------------- | -------------------------- |
| **Elite**  | <1 hour           | ✅ 30-60 min (CI + deploy) |
| **High**   | 1 day to 1 week   |                            |
| **Medium** | 1 week to 1 month |                            |
| **Low**    | >1 month          |                            |

**My actual lead time breakdown:**

| Stage           | Time                     |
| --------------- | ------------------------ |
| **Code review** | 15-30 min (async)        |
| **CI pipeline** | 10-15 min (build + test) |
| **Deploy**      | 5-10 min (Heroku)        |
| **Total**       | 30-55 min                |

**How to improve:**

- Fast CI/CD (caching, parallelization)
- Small PRs (easier to review)
- Automate testing (no manual QA bottleneck)
- Deploy in off-peak hours (avoid traffic spikes)

### 3. Change Failure Rate

**Question:** What % of deployments cause incidents?

**Why it matters:**

- High failure rate = low confidence in changes
- Indicates testing gaps
- Predicts customer impact

**Measurement:**

```typescript
changeFailureRate = (failedDeployments / totalDeployments) * 100

// Example
changeFailureRate = (2 failed / 140 total) * 100 = 1.4%
```

**Benchmarks:**

| Level      | Failure Rate | My Project          |
| ---------- | ------------ | ------------------- |
| **Elite**  | 0-15%        | ✅ 2% (98% success) |
| **High**   | 16-30%       |                     |
| **Medium** | 31-45%       |                     |
| **Low**    | >45%         |                     |

**What counts as "failure":**

- Rollback required
- Hotfix deployed within 1 hour
- Production incident (downtime, data loss, security)
- Critical bug reported by users

**My failure tracking:**

```markdown
## Deployment Log (December 2025)

| Date  | Deploy | Result      | Notes                     |
| ----- | ------ | ----------- | ------------------------- |
| 12/01 | #140   | ✅ Success  |                           |
| 12/01 | #141   | ✅ Success  |                           |
| 12/02 | #142   | ❌ Rollback | CORS error, fixed in #143 |
| 12/02 | #143   | ✅ Success  | Hotfix for #142           |
| 12/03 | #144   | ✅ Success  |                           |

**Monthly Stats:**

- Total: 140 deploys
- Failed: 2 (1.4%)
- Success: 98.6%
```

**How to improve:**

- E2E tests (catch integration bugs)
- Staging environment (test before prod)
- Feature flags (disable broken features without deploy)
- Monitoring (detect issues quickly)

### 4. Time to Restore Service (MTTR)

**Question:** How long to recover from incident?

**Why it matters:**

- Downtime costs money ($5K-100K/hour for businesses)
- Customer trust (fast recovery = confidence)
- Indicates incident response process quality

**Measurement:**

```typescript
mttr = incidentResolvedTime - incidentDetectedTime

// Example
mttr = 10:45 - 10:15 = 30 minutes
```

**Benchmarks:**

| Level      | MTTR    | My Project                    |
| ---------- | ------- | ----------------------------- |
| **Elite**  | <1 hour | ✅ 15-30 min (rollback + fix) |
| **High**   | 1 day   |                               |
| **Medium** | 1 week  |                               |
| **Low**    | >1 week |                               |

**My incident response:**

```markdown
## Incident Report: Database Connection Failure

**Detected:** 2025-12-05 10:15 (monitoring alert)  
**Resolved:** 2025-12-05 10:45 (30 minutes)

**Timeline:**

- 10:15 - Alert received (database connection timeout)
- 10:20 - Root cause identified (PostgreSQL auth changed)
- 10:25 - Fix applied (pg_hba.conf update)
- 10:30 - PostgreSQL restarted
- 10:35 - Service restored
- 10:45 - Monitoring confirms stable

**MTTR:** 30 minutes

**Prevention:**

- Document PostgreSQL auth setup
- Add health check for database connection
- Alert if connection pool exhausted
```

**How to improve:**

- Monitoring (detect issues fast)
- Runbooks (documented recovery steps)
- Rollback automation (one-click revert)
- Post-mortems (learn from incidents)

## Beyond DORA: Developer Experience Metrics

### 5. Build Time

**Question:** How long does `yarn build` take?

**Why it matters:**

- Slow builds = slow feedback
- Developers context-switch during builds
- CI/CD is slower

**Measurement:**

```typescript
buildTime = buildEndTime - buildStartTime

// With caching
cachedBuildTime = buildTime (when nothing changed)
```

**My build times:**

| Scenario           | Time (Before Turbo) | Time (After Turbo) | Improvement |
| ------------------ | ------------------- | ------------------ | ----------- |
| **Cold build**     | 3m 45s              | 2m 40s             | 29% faster  |
| **Cached build**   | 3m 45s              | 15s                | 93% faster  |
| **Partial change** | 3m 45s              | 45s                | 80% faster  |

**How to improve:**

- Use Turborepo (caching)
- Parallel builds (build packages simultaneously)
- Incremental builds (only rebuild changed files)
- Prune dependencies (remove unused packages)

### 6. Test Suite Duration

**Question:** How long do all tests take?

**Why it matters:**

- Slow tests = developers skip testing
- Long CI = slow deployments
- Test fatigue (tests become ignored)

**My test breakdown:**

| Test Type             | Count | Duration           | Parallelized    |
| --------------------- | ----- | ------------------ | --------------- |
| **Unit tests**        | 50    | 5s                 | Yes             |
| **Integration tests** | 20    | 15s                | Yes             |
| **E2E tests**         | 25    | 120s               | Yes (3 workers) |
| **Total**             | 95    | **140s (2.3 min)** |                 |

**How to improve:**

- Parallelize (run tests simultaneously)
- Skip unchanged tests (only test affected files)
- Mock external APIs (no network calls)
- Database fixtures (fast test data setup)

**Playwright optimization:**

```typescript
// playwright.config.ts
export default defineConfig({
  workers: 3, // 3 parallel browsers
  fullyParallel: true,
  retries: 2, // Auto-retry flaky tests
  timeout: 30000,
})
```

**Result:** 25 E2E tests in 120 seconds (vs 10+ minutes sequentially).

### 7. PR Review Time

**Question:** How long until PR is reviewed and merged?

**Why it matters:**

- Long waits = context switching
- Blocked work (can't continue)
- Motivation drain (excitement fades)

**Measurement:**

```typescript
prReviewTime = prMergedTime - prOpenedTime
```

**My PR times:**

| PR Size    | Lines Changed | Review Time | Target   |
| ---------- | ------------- | ----------- | -------- |
| **Small**  | <100 lines    | 15-30 min   | <1 hour  |
| **Medium** | 100-300 lines | 1-2 hours   | <4 hours |
| **Large**  | 300-500 lines | 3-5 hours   | <1 day   |
| **Huge**   | 500+ lines    | 1-2 days    | Avoid    |

**How to improve:**

- Small PRs (<200 lines)
- Clear description (what, why, how)
- Screenshots/video (for UI changes)
- Self-review before requesting review
- Async review (don't wait for sync meeting)

**PR template:**

```markdown
## What

Add team member section component

## Why

Client needs team page with photo grid

## How

- Created Strapi content type
- Built React component
- Added E2E test

## Screenshots

[Screenshot of component]

## Testing

- Manual: Tested on mobile, tablet, desktop
- E2E: Added test for 4-member grid
- CI: All tests passing
```

### 8. CI/CD Success Rate

**Question:** What % of CI runs pass?

**Why it matters:**

- Low rate = unreliable tests (ignored)
- Flaky tests waste time (re-runs)
- Broken main branch (blocks development)

**Measurement:**

```typescript
ciSuccessRate = (successfulRuns / totalRuns) * 100

// Example
ciSuccessRate = (138 / 140) * 100 = 98.6%
```

**My CI stats:**

| Month        | Runs | Successes | Failures | Rate                 |
| ------------ | ---- | --------- | -------- | -------------------- |
| **Dec 2025** | 140  | 138       | 2        | 98.6%                |
| **Nov 2025** | 135  | 132       | 3        | 97.8%                |
| **Oct 2025** | 120  | 73        | 47       | 60.8% (before fixes) |

**Industry average:** 85%  
**My result:** 98% (13 points above average)

**How I achieved 98%:**

1. Fixed flaky tests (deterministic data)
2. Health check polling (wait for services)
3. Retry logic (exponential backoff)
4. Environment cleanup (fresh database per run)

### 9. Developer Onboarding Time

**Question:** How long until new developer ships first PR?

**Why it matters:**

- Indicates documentation quality
- Reflects codebase complexity
- Measures team support

**Measurement:**

```typescript
onboardingTime = firstPRMergedDate - startDate

// Example
onboardingTime = 3 days
```

**My onboarding checklist:**

| Task                        | Time       | Documentation         |
| --------------------------- | ---------- | --------------------- |
| **Clone repo**              | 5 min      | README.md             |
| **Install dependencies**    | 10 min     | Installation guide    |
| **Start dev servers**       | 15 min     | Quick start guide     |
| **Understand architecture** | 2 hours    | Architecture docs     |
| **Fix first bug**           | 4 hours    | Troubleshooting guide |
| **Ship first PR**           | 1 day      | Component workflow    |
| **Total**                   | **3 days** | Comprehensive docs    |

**How to improve:**

- Video walkthrough (show don't tell)
- Pair programming session (answer questions live)
- Good first issues (labeled in GitHub)
- Documentation-first development (guides exist)

### 10. Code Review Coverage

**Question:** What % of PRs get reviewed before merge?

**Why it matters:**

- Catches bugs before production
- Knowledge sharing (team learns from each other)
- Code quality (multiple eyes)

**Measurement:**

```typescript
reviewCoverage = (reviewedPRs / totalPRs) * 100

// Example
reviewCoverage = (135 / 140) * 100 = 96.4%
```

**My policy:**

- ✅ All PRs require review (GitHub branch protection)
- ✅ Exception: Hotfixes can merge without review (emergency only)
- ✅ Self-merge allowed for docs-only changes

**Review depth:**

| Review Type         | % of PRs | When to Use                         |
| ------------------- | -------- | ----------------------------------- |
| **Quick scan**      | 30%      | Docs, config, small fixes           |
| **Standard review** | 60%      | Features, refactors                 |
| **Deep review**     | 10%      | Architecture, security, data models |

### 11. Technical Debt Ratio

**Question:** What % of time is spent on new features vs fixing old code?

**Why it matters:**

- High debt = slow feature velocity
- Indicates code quality
- Predicts future maintenance burden

**Measurement:**

```typescript
techDebtRatio = (maintenanceTime / totalDevTime) * 100

// Example
techDebtRatio = (8 hours / 40 hours) * 100 = 20%
```

**My monthly breakdown:**

| Activity         | Hours | %    |
| ---------------- | ----- | ---- |
| **New features** | 60    | 50%  |
| **Bug fixes**    | 24    | 20%  |
| **Refactoring**  | 12    | 10%  |
| **Docs**         | 12    | 10%  |
| **Meetings**     | 12    | 10%  |
| **Total**        | 120   | 100% |

**Tech debt ratio:** 20% (bug fixes) + 10% (refactoring) = **30%**

**Target:** <30% (more time on features than maintenance)

**How to improve:**

- Write tests (prevent bugs)
- Refactor during feature work (not separate sprints)
- Document architecture decisions (reduce confusion)
- Code reviews (catch issues early)

## Metrics to Avoid (Vanity Metrics)

### ❌ Lines of Code

**Problem:** Encourages verbose, complex code

**Better metric:** Lines deleted (simplification is good)

---

### ❌ Number of Commits

**Problem:** Encourages tiny, meaningless commits

**Better metric:** Deployed features per week

---

### ❌ Hours Worked

**Problem:** Rewards time, not outcomes

**Better metric:** Lead time for changes

---

### ❌ Story Points Completed

**Problem:** Gameable, subjective estimates

**Better metric:** Cycle time (actual time to ship)

---

### ❌ Code Coverage %

**Problem:** Easy to hit 100% with bad tests

**Better metric:** Change failure rate (do tests catch bugs?)

## How to Start Tracking

### Week 1: Set Up Basic Tracking

**DORA metrics (GitHub Actions):**

```yaml
# .github/workflows/dora-metrics.yml
name: DORA Metrics
on:
  push:
    branches: [main]
  workflow_run:
    workflows: ["CI"]
    types: [completed]

jobs:
  track-metrics:
    runs-on: ubuntu-latest
    steps:
      - name: Record deployment
        run: |
          echo "Deployment at $(date)" >> deployments.log
          echo "Status: ${{ job.status }}" >> deployments.log
```

## Key Takeaways

✅ **Track outcomes, not activity** (deploys, not commits)  
✅ **DORA metrics are standard** (deployment frequency, lead time, failure rate, MTTR)  
✅ **Developer experience matters** (build time, test duration, satisfaction)  
✅ **Avoid vanity metrics** (lines of code, hours worked, story points)  
✅ **Elite benchmarks achievable** (98% CI success, 20 deploys/day, <1 hour MTTR)  
✅ **Measure to improve** (track trends, not absolute numbers)  
✅ **Survey developers** (happiness predicts retention)

**Bottom line:** Measure what drives outcomes, not what's easy to count.

## Next Steps

**If you're not tracking anything:**

1. Start with DORA metrics (deployment frequency, lead time)
2. Add CI success rate (easiest to measure)
3. Track build times (Turborepo profiling)
4. Survey developers (quarterly, 5 questions)

**If you're tracking the wrong things:**

1. Audit current metrics (do they drive right behavior?)
2. Stop tracking vanity metrics (lines of code, commits)
3. Replace with outcome metrics (lead time, failure rate)
4. Review monthly (are we improving?)
