## The $3,000 Mistake That Took 2 Seconds

It was December 2, 2025. I was setting up E2E tests for my Strapi CMS. I ran a seed script to populate test data.

**Two seconds later, my entire database was gone.**

203 content entities. 331 media assets. 10 meticulously crafted pages. All deleted.

The command that destroyed everything:

```bash
DROP SCHEMA IF EXISTS public CASCADE;
CREATE SCHEMA public;
```

Embedded in what I thought was a "harmless" seed script.

Here's how a 1-day-old backup saved $3,000 of content value, what I learned about disaster recovery, and the prevention system I built to ensure it never happens again.

## Why This Happened

### Mistake #1: Wrong Script for Wrong Environment

The seed script was designed for **CI environments** that start fresh every time:

```json
// package.json (CI-focused)
{
  "scripts": {
    "seed:e2e": "./database/seeds/seed-e2e-data.sh"
  }
}
```

**CI environment characteristics:**

- ✅ Fresh database every run
- ✅ No existing content
- ✅ Destructive operations safe
- ✅ Isolation guaranteed

**Development environment characteristics:**

- ❌ Has valuable content
- ❌ Accumulates work over days/weeks
- ❌ Destructive operations DANGEROUS
- ❌ Shared with manual testing

**I used a CI script in development.** Classic environment mismatch.

### Mistake #2: No Explicit Warning

The script had NO warning about data deletion:

```bash
#!/bin/bash
# seed-e2e-data.sh

# Drops entire database schema
psql -h localhost -U strapi -d strapi_dev -c \
  "DROP SCHEMA IF EXISTS public CASCADE; CREATE SCHEMA public;"

# Seeds test data
node database/seeds/run-seed.js
```

**What it should have had:**

```bash
#!/bin/bash
# CI USE ONLY - THIS WILL DELETE ALL DATA
# For local development, use: seed-e2e-data-safe.sh

echo "⚠️  WARNING: This script will DELETE ALL DATABASE CONTENT"
echo "Press Ctrl+C to cancel, or wait 5 seconds to proceed..."
sleep 5

# ... destructive operations
```

### Mistake #3: Tunnel Vision on Task

I was focused on "get E2E tests working" and didn't consider:

- Is this script safe for my environment?
- Do I have a recent backup?
- What's the worst-case scenario?
- Should I test this on a copy first?

**Lesson:** When running unfamiliar scripts, slow down and verify.

## Strapi Export vs pg_dump: The Right Tool

### Why I Used Strapi Export (Not pg_dump)

Both tools create backups, but they serve different purposes:

#### Option 1: pg_dump (PostgreSQL Native)

**What it backs up:**

- ✅ Raw database tables
- ✅ Exact schema structure
- ✅ All PostgreSQL-specific features
- ✅ Database users, permissions

**Limitations:**

- ❌ Strapi-specific metadata not portable
- ❌ Can't import into different Strapi versions easily
- ❌ Media files stored separately (not in database)
- ❌ Requires matching PostgreSQL version

**Use case:** Infrastructure-level backups, database migrations

```bash
# Create backup
pg_dump -h localhost -U strapi -d strapi_dev -F tar -f backup.tar

# Restore
pg_restore -h localhost -U strapi -d strapi_dev backup.tar
```

#### Option 2: Strapi Export (CMS Native) ✅ WINNER

**What it backs up:**

- ✅ All content entities (pages, posts, etc.)
- ✅ Media files (images, videos, PDFs)
- ✅ Relations between content
- ✅ Configuration (API tokens, permissions)
- ✅ Content type schemas

**Advantages:**

- ✅ Version-agnostic (works across Strapi versions)
- ✅ Includes media files in single archive
- ✅ Human-readable format (JSONL)
- ✅ Selective restore possible
- ✅ Works across different databases (PostgreSQL → SQLite)

**Use case:** Content backups, environment sync, disaster recovery

```bash
# Create backup
yarn strapi export --no-encrypt -f backup.tar.gz

# Restore
yarn strapi import -f backup.tar.gz --force
```

### Why Strapi Export Saved Me

1. **Single Archive:** Everything in one `.tar.gz` file (entities + media)
2. **Fast Import:** 5 minutes to restore 28 MB of content
3. **Verification:** Human-readable JSON, could inspect before importing
4. **Complete Recovery:** Every entity, every asset, every relationship restored

**Result:** Perfect restoration with zero manual intervention.

## Prevention System: Safe Seed Scripts

After recovery, I created a **dual-script system** to prevent this forever:

### Script 1: Destructive (CI Only)

**File:** `scripts/seed-e2e-data.sh`

```bash
#!/bin/bash
# ⚠️  CI USE ONLY - THIS WILL DELETE ALL DATA ⚠️
# For local development, use: seed-e2e-data-safe.sh

echo "🚨 WARNING: DESTRUCTIVE OPERATION"
echo "This will DROP the entire public schema"
echo "Only use in CI environments with fresh databases"
echo ""
echo "Press Ctrl+C to cancel, or wait 5 seconds..."
sleep 5

# Drop and recreate schema (DESTRUCTIVE)
psql -h localhost -U strapi -d strapi_dev -c \
  "DROP SCHEMA IF EXISTS public CASCADE; CREATE SCHEMA public;"

# Seed test data
node database/seeds/run-seed.js
```

**Usage:**

```json
// package.json
{
  "scripts": {
    "seed:e2e": "./database/seeds/seed-e2e-data.sh" // CI only
  }
}
```

**When to use:** GitHub Actions, GitLab CI, automated testing

### Script 2: Safe (Local Development)

**File:** `scripts/seed-e2e-data-safe.sh`

```bash
#!/bin/bash
# ✅ SAFE for local development
# Only creates/updates E2E test page, preserves existing content

echo "✅ Safe seeding mode"
echo "Existing content will be preserved"

# Run safe seed (no schema drop)
node database/seeds/run-seed-safe.js
```

**Safe seed logic:**

```typescript
// database/seeds/e2e-test-data-safe.ts

export async function seedE2EDataSafe({ strapi }) {
  console.log("🌱 Seeding E2E test data (SAFE mode)")

  // Check if E2E test page already exists
  const existingPages = await strapi.documents("api::page.page").findMany({
    filters: { slug: "e2e-test-page" },
  })

  const pageData = {
    title: "E2E Test Page",
    slug: "e2e-test-page",
    sections: [
      /* ... test sections ... */
    ],
  }

  if (existingPages.length > 0) {
    // Update existing page (idempotent)
    console.log("📝 Updating existing E2E test page")
    await strapi.documents("api::page.page").update({
      documentId: existingPages[0].documentId,
      data: pageData,
    })
  } else {
    // Create new page
    console.log("✨ Creating new E2E test page")
    await strapi.documents("api::page.page").create({
      data: pageData,
    })
  }

  console.log("✅ E2E test data seeded successfully (safe mode)")
}
```

**Usage:**

```json
// package.json
{
  "scripts": {
    "seed:e2e:safe": "./database/seeds/seed-e2e-data-safe.sh" // Local dev
  }
}
```

**When to use:** Local development, anytime you have existing content

### Environment-Specific Usage

| Environment | Script           | Destructive? | Command              |
| ----------- | ---------------- | ------------ | -------------------- |
| CI          | seed-e2e.sh      | ✅ YES       | `yarn seed:e2e`      |
| Local Dev   | seed-e2e-safe.sh | ❌ NO        | `yarn seed:e2e:safe` |
| Production  | NEVER            | N/A          | Use migrations       |

## Backup Strategy Lessons

### What Worked

**✅ Daily Exports**

I had created this backup the day before:

```bash
# Automated daily backup (cron job)
0 2 * * * cd ~/strapi-project && yarn strapi export --no-encrypt \
  -f backups/daily/backup-$(date +\%Y\%m\%d).tar.gz
```

**Result:** 1-day-old backup available immediately

**✅ Organized Directory Structure**

```
backups/
├── daily/              # Automated daily backups (7-day retention)
├── weekly/             # Weekly backups (4-week retention)
├── recovery/           # Critical recovery points
└── pre-migration/      # Before major changes
```

**Result:** Easy to find the right backup quickly

**✅ Strapi Export Format**

Using Strapi's native format meant:

- Single file with everything
- Fast import (5 minutes)
- Version-agnostic
- Human-readable (could inspect if needed)

### What I Improved

**❌ No Automated Verification**

I didn't know if backups were valid until I needed them.

**Fix:** Added verification script:

```bash
#!/bin/bash
# verify-backup.sh

BACKUP_FILE=$1

# Test if backup can be extracted
if tar -tzf "$BACKUP_FILE" > /dev/null 2>&1; then
  echo "✅ Backup archive is valid"

  # Check for required files
  if tar -tzf "$BACKUP_FILE" | grep -q "metadata.json"; then
    echo "✅ Metadata present"
  else
    echo "❌ Missing metadata.json"
    exit 1
  fi
else
  echo "❌ Backup archive is corrupted"
  exit 1
fi
```

**❌ No Off-Site Storage**

All backups were on the same machine as the database.

**Fix:** Added S3 sync:

```bash
#!/bin/bash
# sync-to-s3.sh

aws s3 sync backups/ s3://my-strapi-backups/ \
  --exclude "daily/*" \
  --include "recovery/*" \
  --include "weekly/*"
```

**❌ No Retention Policy**

Backups accumulated indefinitely, wasting disk space.

**Fix:** Added cleanup script:

```bash
#!/bin/bash
# cleanup-old-backups.sh

# Keep daily backups for 7 days
find backups/daily/ -type f -mtime +7 -delete

# Keep weekly backups for 30 days
find backups/weekly/ -type f -mtime +30 -delete

# Never auto-delete recovery backups (manual only)
```

### Recommended Backup Schedule

**Daily Backups (Automated):**

```bash
# Cron: 2 AM every day
0 2 * * * cd ~/strapi && yarn strapi export --no-encrypt \
  -f backups/daily/backup-$(date +\%Y\%m\%d).tar.gz
```

**Weekly Backups (Automated):**

```bash
# Cron: 2 AM every Sunday
0 2 * * 0 cd ~/strapi && yarn strapi export --no-encrypt \
  -f backups/weekly/backup-$(date +\%Y\%m\%d).tar.gz
```

**Pre-Operation Backups (Manual):**

```bash
# Before risky operations (migrations, destructive scripts)
yarn strapi export --no-encrypt -f backups/recovery/pre-operation-$(date +\%Y\%m\%d-%H\%M\%S).tar.gz
```

## Prevention Checklist

### Before Running ANY Database Script

**🔍 Environment Check**

- [ ] Verify which environment you're in (dev/staging/prod)
- [ ] Confirm database has content you care about
- [ ] Check if script is environment-specific

**💾 Backup Verification**

- [ ] Check when last backup was created
- [ ] Verify backup file exists and is valid
- [ ] Ensure backup is recent enough (< 24 hours preferred)
- [ ] Consider creating fresh backup before proceeding

**📖 Script Review**

- [ ] Read script contents (don't run blindly)
- [ ] Look for `DROP`, `DELETE`, `TRUNCATE` commands
- [ ] Check for `CASCADE` flags (deletes related data)
- [ ] Understand what will be modified/deleted

**✅ Confirmation**

- [ ] Are you using the right script for your environment?
- [ ] Do you have a tested backup?
- [ ] Have you warned team members (if shared database)?
- [ ] Is this the right time (not Friday 5pm)?

**Golden Rule:** If uncertain, create a backup first. Always.

## Key Takeaways

### What I Learned

1. **Environment-Specific Tools Matter**

   - CI scripts designed for fresh environments
   - Development scripts must preserve existing content
   - Never assume a script is safe across environments

2. **Backups Are Insurance**

   - 1-day-old backup saved $3,000 and 27 hours
   - Daily automated exports cost nothing, save everything
   - Strapi export > pg_dump for content recovery

3. **Idempotent Scripts Prevent Disasters**

   - Check-then-update pattern is safer than delete-then-create
   - Safe scripts can run multiple times without harm
   - Explicit warnings prevent accidental destruction

4. **Recovery Speed Matters**
   - 3 hours total recovery time (including verification)
   - Single-file backups (Strapi export) are fastest
   - Having a tested restore procedure saves time
