## The Problem: Fetch Has No Timeout

Here's a fact that surprises many JavaScript developers:

**The native `fetch()` API has no timeout.**

```javascript
// This will hang FOREVER if the server never responds
const response = await fetch("https://slow-api.example.com/data")
const data = await response.json()
```

If the server:

- Takes 5 minutes to respond → You wait 5 minutes
- Never responds → You wait forever
- Crashes mid-request → You wait forever

**No timeout. No escape hatch. Just infinite waiting.**

## The Solution: AbortController

JavaScript's `AbortController` provides timeout capability for fetch:

```typescript
// apps/ui/src/lib/strapi-api/base.ts (AFTER fix)

public async fetchAPI(path: string, params: any, requestInit?: RequestInit) {
  const { url, headers } = await this.prepareRequest(path, params, requestInit)

  // Create AbortController for timeout
  const controller = new AbortController()
  const timeoutMs = 30000
  const timeoutId = setTimeout(() => controller.abort(), timeoutMs)

  try {
    const response = await fetch(url, {
      ...requestInit,
      signal: controller.signal, // ✅ KEY: Add abort signal
      headers,
    })

    clearTimeout(timeoutId) // ✅ CLEANUP: Clear on success

    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`)
    }

    return response.json()
  } catch (error: any) {
    clearTimeout(timeoutId) // ✅ CLEANUP: Clear on error

    // Handle timeout specifically
    if (error.name === 'AbortError') {
      const appError = {
        name: 'Request Timeout',
        message: `API request to ${url} timed out after ${timeoutMs}ms`,
        status: 408,
      }
      console.error('[API] Request timeout:', appError)
      throw new Error(JSON.stringify(appError))
    }

    // Re-throw other errors
    throw error
  }
}
```

### Key Components

**1. Create AbortController**

```typescript
const controller = new AbortController()
const timeoutMs = 30000
const timeoutId = setTimeout(() => controller.abort(), timeoutMs)
```

**What this does:**

- `new AbortController()` creates controller instance
- `setTimeout(() => controller.abort(), 30000)` schedules abort after 30s
- Returns `timeoutId` for cleanup later

**2. Pass Signal to Fetch**

```typescript
const response = await fetch(url, {
  signal: controller.signal, // ← Connects fetch to abort controller
  // ... other options
})
```

**What this does:**

- `controller.signal` links the fetch request to the controller
- When `controller.abort()` is called, fetch throws `AbortError`
- Fetch stops waiting and fails fast

**3. Cleanup Timeout (Success Path)**

```typescript
clearTimeout(timeoutId) // After successful response
```

**Why this matters:**

- If response arrives in 2s, we don't want abort at 30s
- `clearTimeout()` cancels the pending abort
- Prevents false timeout errors after success

**4. Cleanup Timeout (Error Path)**

```typescript
catch (error) {
  clearTimeout(timeoutId) // CRITICAL: Clear in catch block too!

  if (error.name === 'AbortError') {
    // Handle timeout specifically
  }
  throw error
}
```

**Why this matters:**

- If fetch fails for OTHER reasons (network error, 404, etc.), we still need cleanup
- Without cleanup, timeout might fire AFTER error is thrown
- Could cause confusing double-error scenarios

## Reusable Pattern: fetchWithTimeout()

Here's a drop-in helper you can use anywhere:

```typescript
/**
 * Fetch with automatic timeout using AbortController
 *
 * @param url - URL to fetch
 * @param options - Standard fetch options
 * @param timeoutMs - Timeout in milliseconds (default 10000)
 * @returns Promise<Response>
 * @throws AbortError if timeout exceeded
 *
 * @example
 * const response = await fetchWithTimeout('https://api.example.com/data')
 * const data = await response.json()
 *
 * @example
 * const response = await fetchWithTimeout(
 *   'https://api.example.com/slow',
 *   { method: 'POST', body: JSON.stringify({...}) },
 *   30000 // 30s timeout
 * )
 */
export async function fetchWithTimeout(
  url: string,
  options?: RequestInit,
  timeoutMs: number = 10000
): Promise<Response> {
  const controller = new AbortController()
  const timeoutId = setTimeout(() => controller.abort(), timeoutMs)

  try {
    const response = await fetch(url, {
      ...options,
      signal: controller.signal,
    })

    clearTimeout(timeoutId)
    return response
  } catch (error: any) {
    clearTimeout(timeoutId)

    if (error.name === "AbortError") {
      throw new Error(`Request to ${url} timed out after ${timeoutMs}ms`)
    }

    throw error
  }
}
```

### Usage Examples

**Simple GET request:**

```typescript
const response = await fetchWithTimeout("https://api.example.com/users")
const users = await response.json()
```

**POST with custom timeout:**

```typescript
const response = await fetchWithTimeout(
  "https://api.example.com/data",
  {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ name: "Herman" }),
  },
  30000 // 30-second timeout
)
```

**With error handling:**

```typescript
try {
  const response = await fetchWithTimeout("https://api.example.com/slow")
  const data = await response.json()
  console.log("Success:", data)
} catch (error) {
  if (error.message.includes("timed out")) {
    console.error("Request took too long")
  } else {
    console.error("Network error:", error)
  }
}
```

## Common Pitfalls (And How to Avoid Them)

### ❌ Pitfall 1: Forgetting to Clear Timeout

```typescript
// WRONG: No cleanup
const controller = new AbortController()
setTimeout(() => controller.abort(), 10000)

const response = await fetch(url, { signal: controller.signal })
// ❌ Timeout still firing even after success!
```

**Problem:** Timeout fires 10s later even if request succeeded in 1s.

**Solution:** Always `clearTimeout()` in success AND error paths:

```typescript
// CORRECT: Cleanup in both paths
const controller = new AbortController()
const timeoutId = setTimeout(() => controller.abort(), 10000)

try {
  const response = await fetch(url, { signal: controller.signal })
  clearTimeout(timeoutId) // ✅ Clear on success
  return response
} catch (error) {
  clearTimeout(timeoutId) // ✅ Clear on error
  throw error
}
```

### ❌ Pitfall 2: Not Handling AbortError Specifically

```typescript
// WRONG: Generic error handling
try {
  const response = await fetch(url, { signal: controller.signal })
} catch (error) {
  console.error("Request failed:", error) // ❌ Timeout looks like network error
}
```

**Problem:** AbortError gets logged as generic "request failed," hiding the real issue.

**Solution:** Check `error.name === 'AbortError'`:

```typescript
// CORRECT: Specific timeout handling
try {
  const response = await fetch(url, { signal: controller.signal })
} catch (error: any) {
  if (error.name === "AbortError") {
    console.error("Request timed out") // ✅ Clear timeout message
  } else {
    console.error("Network error:", error) // ✅ Other errors separate
  }
}
```

### ❌ Pitfall 3: Creating New Controller in Loop

```typescript
// WRONG: Controller inside loop
for (const item of items) {
  const controller = new AbortController() // ❌ New controller each iteration
  const timeout = setTimeout(() => controller.abort(), 5000)

  await fetch(`/api/${item.id}`, { signal: controller.signal })
  // ❌ What if we break early? Timeouts still pending!
}
```

**Problem:** Pending timeouts from early iterations keep running.

**Solution:** Track timeouts and clean up on exit:

```typescript
// CORRECT: Cleanup on early exit
const timeouts: NodeJS.Timeout[] = []

try {
  for (const item of items) {
    const controller = new AbortController()
    const timeoutId = setTimeout(() => controller.abort(), 5000)
    timeouts.push(timeoutId)

    await fetch(`/api/${item.id}`, { signal: controller.signal })
    clearTimeout(timeoutId) // ✅ Clear after each request
  }
} finally {
  timeouts.forEach(clearTimeout) // ✅ Cleanup any remaining
}
```

### ❌ Pitfall 4: Reusing Same Controller

```typescript
// WRONG: Reusing aborted controller
const controller = new AbortController()
controller.abort() // Manual abort

// Later...
await fetch(url1, { signal: controller.signal }) // ❌ Already aborted!
await fetch(url2, { signal: controller.signal }) // ❌ Already aborted!
```

**Problem:** Once aborted, a controller can't be "un-aborted."

**Solution:** Create new controller for each independent request:

```typescript
// CORRECT: New controller per request
async function fetchData(url: string) {
  const controller = new AbortController() // ✅ Fresh controller
  const timeoutId = setTimeout(() => controller.abort(), 10000)

  try {
    const response = await fetch(url, { signal: controller.signal })
    clearTimeout(timeoutId)
    return response
  } catch (error) {
    clearTimeout(timeoutId)
    throw error
  }
}

await fetchData(url1) // ✅ Independent controller
await fetchData(url2) // ✅ Independent controller
```

## When to Use AbortController Timeout

### ✅ Good Use Cases

**1. Server-Side Rendering (SSR)**

```typescript
// Next.js getServerSideProps with timeout
export async function getServerSideProps() {
  const data = await fetchWithTimeout(
    "https://api.example.com/data",
    undefined,
    5000 // 5s timeout (don't delay page render)
  )
  return { props: { data } }
}
```

**2. API Client Libraries**

```typescript
class APIClient {
  async get(endpoint: string) {
    return fetchWithTimeout(`${this.baseUrl}${endpoint}`, undefined, 10000)
  }
}
```

**3. Health Check Polling**

```typescript
async function checkHealth() {
  try {
    await fetchWithTimeout("http://localhost:1337/admin", undefined, 2000)
    return true
  } catch {
    return false
  }
}
```

**4. E2E Test API Calls**

```typescript
test("API responds within 5s", async () => {
  const response = await fetchWithTimeout("/api/users", undefined, 5000)
  expect(response.ok).toBe(true)
})
```

### ❌ Less Ideal Use Cases

**1. User-Facing Interactive Requests**

```typescript
// AVOID: Fixed timeout for user actions
button.onclick = async () => {
  const data = await fetchWithTimeout("/search", undefined, 3000)
  // ❌ What if user has slow connection? They get timeout error.
}
```

**Better:** Use loading states, let user cancel manually:

```typescript
// BETTER: User-controlled abort
const controller = new AbortController()

button.onclick = async () => {
  cancelButton.onclick = () => controller.abort() // User cancels
  const data = await fetch("/search", { signal: controller.signal })
}
```

**2. File Uploads**

```typescript
// AVOID: Fixed timeout for uploads
await fetchWithTimeout(
  "/upload",
  {
    method: "POST",
    body: formData,
  },
  10000
)
// ❌ Large files might legitimately take > 10s
```

**Better:** Use progress tracking, dynamic timeout based on file size.

## Key Takeaways

### What I Learned

1. **Fetch has no built-in timeout**

   - Native `fetch()` will wait forever
   - No escape hatch without AbortController
   - Can cause test hangs, resource exhaustion

2. **AbortController is the standard solution**

   - Designed specifically for this use case
   - Works with fetch, axios (v0.22+), any AbortSignal-aware API
   - Well-supported across modern browsers

3. **Cleanup is mandatory, not optional**

   - `clearTimeout()` in both success and error paths
   - Memory leaks if timeouts keep firing
   - Confusing errors if cleanup skipped

4. **Timeout values matter**
   - Too short: False positives (valid requests timeout)
   - Too long: Slow failure detection
   - Context-dependent: SSR (5s) vs file upload (60s+)

### Quick Implementation Checklist

When adding timeout to fetch:

- [ ] Create `new AbortController()`
- [ ] Set `setTimeout(() => controller.abort(), timeoutMs)`
- [ ] Store `timeoutId` for cleanup
- [ ] Pass `signal: controller.signal` to fetch
- [ ] `clearTimeout(timeoutId)` after successful response
- [ ] `clearTimeout(timeoutId)` in catch block (error path)
- [ ] Check `error.name === 'AbortError'` for timeout detection
- [ ] Choose appropriate timeout value for use case
