## Issue #1: Strapi API Timeouts (41 Tests Blocked)

### The Problem

**All 41 Error Handling tests** had the same failure:

```
Test timeout of 30000ms exceeded.

Error: page.goto: Test timeout of 30000ms exceeded.
Call log:
  - navigating to "http://localhost:3000/en/e2e-test-page", waiting until "networkidle"
```

Every single error handling test started with `page.goto('/en/e2e-test-page')` and **timed out at 30 seconds**.

### The Wrong Hypothesis

**First thought:** "The page doesn't exist in Strapi."

I checked Strapi admin. The page **was there**: Page ID 13, slug `e2e-test-page`, status Published.

**Second thought:** "The route is broken."

I tested manually: `curl http://localhost:3000/en/e2e-test-page` → **200 OK**. Page rendered perfectly.

**Third thought:** "Tests are using wrong URL."

Checked test code: `await page.goto('http://localhost:3000/en/e2e-test-page')` → **Correct**.

### The Real Root Cause

After 4 hours of dead ends, I found it: **No timeout on Strapi API fetch calls**.

```typescript
// apps/ui/src/lib/strapi-api/base.ts (BEFORE fix)

public async fetchAPI(path: string, params: any, requestInit?: RequestInit) {
  const { url, headers } = await this.prepareRequest(path, params, requestInit)

  const response = await fetch(url, {  // ❌ No timeout!
    ...requestInit,
    headers,
  })

  return response.json()
}
```

**Why this caused timeouts:**

1. Error handling tests ran **9 workers in parallel**
2. Each worker made SSR requests to Next.js dev server
3. Next.js dev server got **overwhelmed** by concurrent requests
4. Fetch calls **hung indefinitely** waiting for slow responses
5. Playwright timed out at 30s before fetch ever returned

**The cascade effect:**

- Worker 1 request: 2s response time ✅
- Worker 2 request: 4s response time ⚠️
- Worker 3 request: 8s response time ⚠️
- Workers 4-9: **Never responded** ❌

### The Solution

Added **AbortController** with 30-second timeout:

```typescript
// apps/ui/src/lib/strapi-api/base.ts (AFTER fix)

public async fetchAPI(path: string, params: any, requestInit?: RequestInit) {
  const { url, headers } = await this.prepareRequest(path, params, requestInit)

  // Create AbortController for timeout
  const controller = new AbortController()
  const timeoutMs = 30000
  const timeoutId = setTimeout(() => controller.abort(), timeoutMs)

  try {
    const response = await fetch(url, {
      ...requestInit,
      signal: controller.signal, // ✅ Add abort signal
      headers,
    })

    clearTimeout(timeoutId) // ✅ Cleanup on success
    return response.json()
  } catch (error: any) {
    clearTimeout(timeoutId) // ✅ Cleanup on error

    if (error.name === 'AbortError') {
      throw new Error(`Strapi API timeout after ${timeoutMs}ms`)
    }
    throw error
  }
}
```

### Results

**Before:** 4/45 Error Handling tests passing (9%)  
**After:** 34/45 Error Handling tests passing (76%)

**Impact:** 30 tests unblocked, 67% improvement in one fix.

## Issue #2: GDPR Checkbox Blocking (10 Tests Failing)

### The Problem

Newsletter and error handling tests **couldn't click submit buttons**:

```
Error: locator.click: Test timeout of 30000ms exceeded.
Call log:
  - waiting for locator('button:has-text("Subscribe")').first()
  - locator resolved to <button disabled type="submit"...>
  - attempting click action
  - waiting for element to be visible, enabled and stable
  - element is not enabled ← BLOCKED HERE
```

**Submit buttons stayed disabled** even though the test filled out the form correctly.

### The Root Cause

The tests tried to click the GDPR checkbox **label** instead of the checkbox itself:

```typescript
// WRONG (what tests were doing)
await page.locator('label:has-text("I agree")').click()
// Radix UI doesn't propagate label clicks to hidden checkbox
```

**Why this failed:**

- Radix UI uses a **hidden native checkbox** + **custom styled div**
- Label clicks **don't trigger** `onCheckedChange` event
- React state (`agreedToTerms`) stays `false`
- Submit button remains disabled

### The Solution

**Created polling click helper** that tries multiple strategies:

```typescript
// apps/ui/e2e/utils/test-helpers.ts

export async function waitForCheckbox(
  page: Page,
  options?: { timeout?: number }
): Promise<void> {
  const { timeout = 10000 } = options || {}

  // Try multiple possible checkbox IDs
  const possibleIds = ["privacy-consent", "terms-consent", "gdpr-consent"]

  for (const id of possibleIds) {
    try {
      const checkbox = page.locator(`#${id}`)
      await checkbox.waitFor({ state: "attached", timeout: 2000 })

      // Click the actual checkbox (not label)
      await checkbox.click({ force: true })

      // Verify state changed
      await page.waitForSelector(`#${id}[data-state="checked"]`, {
        timeout: 2000,
      })

      console.log(`✓ GDPR checkbox (${id}) checked successfully`)
      return
    } catch {
      continue // Try next ID
    }
  }

  throw new Error("GDPR checkbox not found with any known ID")
}
```

**Key features:**

- ✅ Tries multiple checkbox IDs (flexibility)
- ✅ Clicks actual checkbox, not label (correct event)
- ✅ Verifies `data-state="checked"` (state confirmation)
- ✅ Polling with fallbacks (resilience)

### Results

**Before:** 14/24 Newsletter tests passing (58%)  
**After:** 24/24 Newsletter tests passing (100%)

**Impact:** 10 tests fixed, 42% improvement.

## Issue #3: Toast Detection Failures (7 Tests Flaky)

### The Problem

Contact form tests **couldn't find success toasts**:

```
Error: expect(locator).toBeVisible() failed

Locator: locator('[role="status"]').filter({ hasText: /sent successfully/i })
Expected: visible
Timeout: 15000ms
Error: element(s) not found
```

**The toast was visible** in the browser, but Playwright couldn't find it.

### The Root Cause

Tests relied on **ARIA role attributes** that Radix UI doesn't guarantee:

```typescript
// BRITTLE (role-based detection)
const toast = page.locator('[role="status"]')
await expect(toast).toBeVisible({ timeout: 15000 })
```

**Why this failed:**

- Radix UI v1.2.1 **may or may not** set `role` attribute
- Depends on variant (success, error, warning)
- Can be `role="region"`, `role="status"`, or **no role**
- Role-based selectors are **unreliable**

### The Solution

**Text-based detection** (what users see):

```typescript
// apps/ui/e2e/utils/test-helpers.ts

export async function waitForSuccessToast(
  page: Page,
  expectedText?: string,
  options?: { timeout?: number }
): Promise<void> {
  const { timeout = 5000 } = options || {}

  const toastLocator = expectedText
    ? page.locator(`text=/${expectedText}/i`)
    : page.locator("text=/success|sent successfully|thank you|subscribed/i")

  await expect(toastLocator).toBeVisible({ timeout })
}

// Usage
await waitForSuccessToast(page, "sent successfully")
```

**Why this works:**

- ✅ Matches **user-visible content** (what users actually see)
- ✅ **Role-agnostic** (works across Radix UI versions)
- ✅ **Faster timeout** (5s instead of 15s)
- ✅ **Reusable** across all forms

### Results

**Before:** 21/42 Contact tests passing (50%)  
**After:** 42/42 Contact tests passing (100%)

**Impact:** 21 tests fixed, 50% improvement.

## Issue #4: Database Wipe Incident (203 Entities Lost)

### The Problem

I ran an E2E seed script to fix test data:

```bash
cd apps/strapi
yarn seed:e2e
```

**30 seconds later, every page in Strapi was gone.** 203 entities deleted, 331 images vanished.

### The Root Cause

The seed script contained this **destructive command**:

```bash
# apps/strapi/scripts/seed-e2e-data.sh (CI ONLY!)

psql -h localhost -U strapi -d strapi_dev -c \
  "DROP SCHEMA IF EXISTS public CASCADE; CREATE SCHEMA public;"
```

**What happened:**

- Script was designed for **CI environments** (throwaway databases)
- I ran it in **development** (30 hours of real content)
- No confirmation prompt, no backup check, no safety net
- **$3,000 of content** deleted in one command

### The Solution (3-Hour Recovery)

**Step 1:** Found 1-day-old backup

```bash
ls -lt apps/strapi/backups/ | head -5
# pre-config-import-backup-20251201-185738.tar.gz ✅
```

**Step 2:** Strapi import

```bash
cd apps/strapi
yarn strapi import -f backups/pre-config-import-backup-20251201-185738/export_*.tar.gz.enc

# Results:
# ✔ entities: 203 transferred (253 KB)
# ✔ assets: 331 transferred (27.4 MB)
# ✔ links: 355 transferred (68.5 KB)
```

**Step 3:** Created safe seed scripts

```typescript
// apps/strapi/database/seeds/e2e-test-data-safe.ts

export async function seedE2EDataSafe(strapi: any) {
  // Check if page exists
  const existingPages = await strapi.documents("api::page.page").findMany({
    filters: { slug: "e2e-test-page" },
  })

  if (existingPages.length > 0) {
    // Update existing (safe)
    await strapi.documents("api::page.page").update({
      documentId: existingPages[0].documentId,
      data: {
        /* test data */
      },
    })
  } else {
    // Create new (safe)
    await strapi.documents("api::page.page").create({
      data: {
        /* test data */
      },
    })
  }
}
```

### Results

**Data loss:** 8 hours of recent edits (vs 30 hours total)  
**Recovery cost:** $1,100 (vs $3,000 if no backup)  
**Prevention:** 0 data loss incidents since (6+ weeks)

**Lesson learned:** Environment-specific scripts are **non-negotiable**.

## Issue #5: Homepage Navigation Timeouts (6 Tests Failing)

### The Problem

```
Test timeout of 60000ms exceeded.
Error: page.goto: Test timeout of 60000ms exceeded.
Call log:
  - navigating to "http://localhost:3000/en", waiting until "domcontentloaded"
```

### The Root Cause

`domcontentloaded` wait strategy **unreliable** with Next.js 15 App Router in dev mode.

### The Solution

**Content-based navigation** (wait for actual elements):

```typescript
// BEFORE (event-based, unreliable)
await page.goto("/en", { waitUntil: "domcontentloaded" })

// AFTER (content-based, reliable)
await page.goto("/en")
await page.waitForSelector("nav", { state: "visible", timeout: 15000 })
```

### Results

**Before:** 3/9 Homepage tests passing (33%)  
**After:** 9/9 Homepage tests passing (100%)

## Issue #6: 404 Status Code Issues (3 Tests Failing)

### The Problem

Tests expected `404` status for non-existent pages, but Next.js dev server returns `200`.

### The Root Cause

**Next.js dev mode quirk:** Even when `notFound()` is called and 404 page renders, dev server returns `200 OK`.

### The Solution

**Check content instead of status code:**

```typescript
// BEFORE (status-based, fails in dev)
const response = await page.goto("/nonexistent")
expect(response?.status()).toBe(404) // ❌ Fails (200 in dev)

// AFTER (content-based, works in dev)
await page.goto("/nonexistent")
await expect(page.locator('h1:has-text("Page Not Found")')).toBeVisible()
```

### Results

**Before:** 36/39 API Integration tests passing (92%)  
**After:** 39/39 API Integration tests passing (100%)

## Issue #7: API Integration Failures (3 Tests Failing)

### The Problem

Tests couldn't detect successful API data fetching from Strapi.

### The Root Cause

Missing **wait-for-selector** before assertions.

### The Solution

```typescript
// BEFORE (race condition)
await page.goto("/en/about")
await expect(page.locator("h1")).toContainText("About Us") // ❌ Too fast

// AFTER (wait for content)
await page.goto("/en/about")
await page.waitForSelector("h1", { state: "visible" })
await expect(page.locator("h1")).toContainText("About Us") // ✅ Reliable
```

### Results

**Before:** 36/39 API Integration tests passing (92%)  
**After:** 39/39 API Integration tests passing (100%)

## The Debugging Workflow That Saved Me

Here's the systematic process I used for each issue:

### Step 1: Categorize by Impact (Not Complexity)

```
Priority 1: Issues blocking 10+ tests
Priority 2: Issues blocking 5-9 tests
Priority 3: Issues blocking 1-4 tests
Priority 4: Edge cases, browser-specific
```

**Don't fix easy issues first.** Fix **high-impact** issues first.

### Step 2: Reproduce Locally (Always)

```bash
# Single test (fastest iteration)
yarn test:e2e newsletter.spec.ts --project=chromium

# Single browser, one test
yarn test:e2e newsletter.spec.ts:41 --project=chromium

# With debugging
yarn test:e2e newsletter.spec.ts --debug
```

**If you can't reproduce locally, you can't fix it.**

### Step 3: Generate Trace Files

```typescript
// playwright.config.ts
use: {
  trace: 'retain-on-failure', // ✅ Keep traces for failed tests
  screenshot: 'only-on-failure',
  video: 'retain-on-failure',
}
```

**Trace files show:**

- DOM snapshot at failure
- Network requests
- Console logs
- Timing information

### Step 4: Read the Trace File Like a Detective

```
test-results/newsletter-should-validate-empty-email-chromium/trace.zip

Extract → Open in Playwright Trace Viewer
```

**Look for:**

- What element was Playwright waiting for?
- What was the DOM state at timeout?
- What network requests were pending?
- What console errors appeared?

### Step 5: Form a Hypothesis

**Bad hypothesis:** "Tests are flaky."  
**Good hypothesis:** "Submit button stays disabled because label clicks don't trigger checkbox state change in Radix UI."

**Specificity matters.** Vague hypotheses lead to random fixes.

### Step 6: Test the Hypothesis (Minimal Reproduction)

```typescript
test("REPRO: checkbox click propagation", async ({ page }) => {
  await page.goto("/newsletter")

  // Try label click
  await page.locator('label:has-text("I agree")').click()

  // Check if state changed
  const checkbox = page.locator("#privacy-consent")
  const dataState = await checkbox.getAttribute("data-state")

  console.log("Checkbox data-state:", dataState)
  // Output: "unchecked" ← PROOF label clicks don't work!
})
```

### Step 7: Implement Fix + Verify

```typescript
// Fix
await page.locator("#privacy-consent").click({ force: true })

// Verify state
await page.waitForSelector('#privacy-consent[data-state="checked"]')

// Verify submit enabled
const submitButton = page.locator('button:has-text("Subscribe")')
await expect(submitButton).toBeEnabled()
```

### Step 8: Document the Fix

**Create troubleshooting entry:**

- **Problem:** What failed?
- **Symptoms:** Error messages, screenshots
- **Root cause:** Why it failed (be specific)
- **Solution:** Code changes made
- **Verification:** How to test the fix

**Future you will thank present you.**

## Key Takeaways

### What I Learned

1. **Prioritize by impact, not complexity**

   - Fix issues blocking 40 tests before issues blocking 3 tests
   - "Easy wins" feel good but don't move the needle

2. **Trace files are your best friend**

   - DOM snapshots show exact state at failure
   - Network tab shows pending requests
   - Console logs reveal hidden errors

3. **Test user-visible behavior, not implementation**

   - Text content > ARIA roles
   - Element presence > DOM structure
   - Actual state > Assumed state

4. **Environment-specific scripts are mandatory**

   - CI scripts ≠ Development scripts
   - Add confirmation prompts for destructive operations
   - Test on throwaway databases first

5. **Documentation pays compound interest**
   - 2,400 lines written = 60+ hours saved in future debugging
   - Each issue documented prevents repeat investigation
   - Team onboarding becomes self-service

### Systematic Debugging Checklist

When you encounter failing E2E tests:

- [ ] **Categorize by impact** (how many tests blocked?)
- [ ] **Reproduce locally** (can you see the failure?)
- [ ] **Generate trace files** (what's the DOM state?)
- [ ] **Form specific hypothesis** (why is it failing?)
- [ ] **Test hypothesis in isolation** (minimal reproduction)
- [ ] **Implement fix** (code change)
- [ ] **Verify fix** (run affected tests)
- [ ] **Document root cause** (for future reference)
