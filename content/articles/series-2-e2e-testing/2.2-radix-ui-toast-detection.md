## The Flaky Test Mystery

December 6th, 2025. My E2E test suite had a problem:

```bash
Contact Form Tests: 21/42 passing (50%)
Newsletter Tests: 8/9 passing (89%)
```

**Same form logic. Same toast component. Wildly different results.**

The contact form tests were flaky—sometimes they'd pass, sometimes they'd timeout looking for the success toast. The newsletter tests? Rock solid.

Here's what the failures looked like:

```
Error: expect(locator).toBeVisible() failed

Locator: locator('[role="status"]').filter({ hasText: /sent successfully/i })
Expected: visible
Timeout: 15000ms
Error: element(s) not found
```

The toast was **definitely showing** in the browser. I could see it with my own eyes. But Playwright couldn't find it.

---

## The Wrong Approach: Role-Based Selectors

Here's what my contact form test looked like:

```typescript
// Contact form test (FAILING)
test("should successfully submit contact form", async ({ page }) => {
  await nameInput.fill("Herman Adu")
  await emailInput.fill("test@example.com")
  await messageTextarea.fill("This is a test message")
  await submitButton.click()

  // Wait for success toast
  const successToast = page.locator('[role="status"]', {
    hasText: /sent successfully|success/i,
  })
  await expect(successToast).toBeVisible({ timeout: 15000 })
})
```

**The assumption:** Radix UI toasts have `role="status"` attribute.

**The reality:** Radix UI v1.2.1 can render toasts with:

- `role="region"` (announcement role)
- `role="status"` (status role)
- **No role attribute at all** (just a `<div>`)

The role attribute **is not guaranteed**. It depends on:

- Radix UI version
- Toast variant (success, error, warning)
- ARIA preferences in configuration
- Browser accessibility features

---

## The Working Approach: Text-Based Detection

Meanwhile, my newsletter tests were passing consistently:

```typescript
// Newsletter test (PASSING)
test("should successfully submit newsletter signup", async ({ page }) => {
  await emailInput.fill("test@example.com")
  await submitButton.click()

  // Wait for success toast (text-based detection)
  const successToast = page.locator("text=/thank you|success/i")
  await expect(successToast).toBeVisible({ timeout: 5000 })
})
```

**Key difference:** Text-based locator instead of role-based.

**Why it works:**

- ✅ Doesn't depend on ARIA roles
- ✅ Works across Radix UI versions
- ✅ Matches visible content (what users see)
- ✅ More resilient to DOM structure changes

## The Solution: Standardized Toast Detection

I fixed this in three steps:

### Step 1: Create Reusable Test Helper

**File:** `apps/ui/e2e/utils/test-helpers.ts`

```typescript
/**
 * Wait for success toast to appear
 *
 * Uses text-based detection to find toast notifications.
 * Works reliably across Radix UI versions regardless of role attributes.
 *
 * @param page - Playwright Page object
 * @param expectedText - Optional specific text to look for
 * @param options - Optional configuration (timeout)
 * @returns Promise that resolves when toast is visible
 *
 * @example
 * // Generic success detection
 * await waitForSuccessToast(page)
 *
 * // Specific message
 * await waitForSuccessToast(page, "sent successfully")
 *
 * // Custom timeout
 * await waitForSuccessToast(page, undefined, { timeout: 10000 })
 */
export async function waitForSuccessToast(
  page: Page,
  expectedText?: string,
  options?: { timeout?: number }
): Promise<void> {
  const { timeout = 5000 } = options || {}

  const toastLocator = expectedText
    ? page.locator(`text=/${expectedText}/i`)
    : page.locator("text=/success|sent successfully|thank you|subscribed/i")

  await expect(toastLocator).toBeVisible({ timeout })
}
```

**Key features:**

- ✅ **Text-based detection** (role-agnostic)
- ✅ **Generic success patterns** (works for all forms)
- ✅ **Custom text matching** (form-specific messages)
- ✅ **Configurable timeout** (default 5s, not 15s)
- ✅ **Works across Radix UI versions**

### Step 2: Add Error Toast Helper (Bonus)

```typescript
/**
 * Wait for error toast to appear
 *
 * Companion to waitForSuccessToast for error state validation.
 *
 * @example
 * await waitForErrorToast(page, "Email is required")
 */
export async function waitForErrorToast(
  page: Page,
  expectedText?: string,
  options?: { timeout?: number }
): Promise<void> {
  const { timeout = 5000 } = options || {}

  const toastLocator = expectedText
    ? page.locator(`text=/${expectedText}/i`)
    : page.locator("text=/error|failed|could not|invalid|required/i")

  await expect(toastLocator).toBeVisible({ timeout })
}
```

## Why This Pattern Works

### 1. Content-Based (What Users See)

**Users don't see ARIA roles.** They see text: "Success!", "Thank you for subscribing!", "Form sent successfully."

Your tests should verify **what users experience**, not implementation details.

### 2. Resilient to Library Changes

Radix UI (or any UI library) can change:

- Internal DOM structure
- ARIA role assignments
- CSS class names
- Data attributes

**Text content changes far less frequently** because it's user-facing.

### 3. Faster Failure Detection

```typescript
// Old approach: 15s timeout (hoping role appears)
await expect(page.locator('[role="status"]')).toBeVisible({ timeout: 15000 })

// New approach: 5s timeout (text appears fast)
await waitForSuccessToast(page) // 5s default
```

**3x faster** test failures = **3x faster debugging cycles**.

### 4. Better Developer Experience

```typescript
// Before: Verbose, implementation-coupled
const successToast = page.locator('[role="status"]').filter({
  hasText: /sent successfully|success/i,
})
await expect(successToast).toBeVisible({ timeout: 15000 })

// After: Clean, intent-revealing
await waitForSuccessToast(page, "sent successfully")
```

## Common Pitfalls (And How to Avoid Them)

### ❌ Pitfall 1: Over-Relying on ARIA Roles

```typescript
// BRITTLE: Depends on Radix UI internals
await page.locator('[role="status"]').waitFor()
await page.locator('[role="alert"]').waitFor()
await page.locator('[role="region"]').waitFor()
```

**Problem:** Roles can change between library versions.

**Solution:** Use text content or data attributes you control.

### ❌ Pitfall 2: Generic Text Matches

```typescript
// TOO GENERIC: Might match other content
await page.locator("text=Success").waitFor()
```

**Problem:** "Success" might appear in headers, buttons, or other toasts.

**Solution:** Be specific with expected text or use scoped locators.

```typescript
// BETTER: Specific message
await waitForSuccessToast(page, "sent successfully")

// OR: Scope to toast container
const toastContainer = page.locator("[data-radix-toast-viewport]")
await expect(toastContainer.locator("text=Success")).toBeVisible()
```

### ❌ Pitfall 3: Long Timeouts Masking Issues

```typescript
// SLOW: 30s timeout hides real problems
await expect(toast).toBeVisible({ timeout: 30000 })
```

**Problem:** If toast doesn't appear in 5s, something is wrong. Waiting 30s just delays discovering the bug.

**Solution:** Use reasonable timeouts (5s for toasts, 10s for API responses).

```typescript
// FAST FAILURE: Fail fast, debug faster
await waitForSuccessToast(page) // 5s default
```

### ❌ Pitfall 4: Not Handling Toast Auto-Dismiss

```typescript
// RACE CONDITION: Toast might auto-dismiss before assertion
await submitButton.click()
await page.waitForTimeout(3000) // Wait for something else
await expect(page.locator("text=Success")).toBeVisible() // Already gone!
```

**Problem:** Toasts auto-dismiss after 3-5 seconds. If you wait too long, the toast disappears.

**Solution:** Check for toast **immediately** after action.

```typescript
// CORRECT: Check immediately after submission
await submitButton.click()
await waitForSuccessToast(page) // Check right away
```

## Key Takeaways

### What I Learned

1. **Test user-visible behavior, not implementation**

   - Text content > ARIA roles
   - What users see > What the DOM contains
   - Stable APIs > Internal library details

2. **Fail fast, debug faster**

   - 5s timeouts > 15s timeouts
   - Immediate assertion > Delayed checks
   - Clear error messages > Ambiguous failures

3. **Consistency across tests matters**

   - Reusable helpers > Copy-paste patterns
   - Standardized structure > Ad-hoc implementations
   - Team conventions > Individual preferences

4. **Simple solutions often win**
   - Text-based locators > Complex role queries
   - Direct assertions > Multiple fallbacks
   - Readable code > Clever abstractions
