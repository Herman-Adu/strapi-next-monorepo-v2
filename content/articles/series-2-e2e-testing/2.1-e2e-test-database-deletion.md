## The 3 PM Panic

It was December 2nd, 2025. I was trying to fix flaky E2E tests. The contact form tests kept failing—50% pass rate wasn't acceptable. I needed consistent seed data for the tests.

I found the seed script: `seed-e2e-data.sh`. The name seemed clear enough. I ran it.

```bash
cd apps/strapi
yarn seed:e2e
```

Thirty seconds later, I refreshed the Strapi admin panel.

**Every single page was gone.**

The navbar? Gone. The footer? Gone. All 10 carefully crafted pages with SEO metadata, images, and content? **Gone.**

My heart dropped. I had just deleted 30 hours of content creation work.

---

## What Went Wrong: The Destructive Line

Here's the culprit—one line buried in the seed script:

```bash
# apps/strapi/scripts/seed-e2e-data.sh

# CI USE ONLY - THIS WILL DELETE ALL DATA
psql -h localhost -U strapi -d strapi_dev -c \
  "DROP SCHEMA IF EXISTS public CASCADE; CREATE SCHEMA public;"
```

**What this does:**

- `DROP SCHEMA public CASCADE` = Delete everything in the database
- `CREATE SCHEMA public` = Rebuild the schema structure
- Intended for **CI environments** that start from scratch
- **Disaster** when run in a development environment with real content

### The Impact

```
❌ 203 entities deleted
❌ 331 media assets vanished (27.4 MB of images)
❌ 355 content links broken
❌ 10 pages (Landing, About, Services, Contact, etc.)
❌ Navbar and Footer components
❌ All locales, permissions, settings
```

**Content Value Lost**: 30 hours of creation work = **$3,000** at $100/hour freelance rate.

## Why I Didn't See It Coming

### Mistake #1: Wrong Tool for the Job

I grabbed a **CI-focused script** for use in **local development**:

| Environment | Database State             | Can Use DROP SCHEMA? |
| ----------- | -------------------------- | -------------------- |
| CI (GitHub) | Fresh, throwaway           | ✅ Yes (safe)        |
| Local Dev   | Real content, days of work | ❌ NO (disaster)     |
| Production  | Customer data              | ❌ NEVER             |

The seed script was designed for CI where every test run starts from a clean slate. In CI, `DROP SCHEMA CASCADE` is **safe and expected**. In development with 30 hours of content, it's a **disaster**.

### Mistake #2: No Safety Checks

The script had **zero safeguards**:

- ❌ No confirmation prompt ("Are you sure?")
- ❌ No environment detection (CI vs dev)
- ❌ No backup verification
- ❌ Warning in comments, but easy to miss

Compare to Git's behavior when you try something destructive:

```bash
# Git protects you
git branch -D main
# error: Cannot delete branch 'main' checked out at '/path/to/repo'

# The seed script? No protection
yarn seed:e2e
# *poof* - your data is gone
```

### Mistake #3: Tunnel Vision

I was laser-focused on "fix the E2E tests." I needed seed data. I found a seed script. I ran it.

**I didn't ask:**

- What does this script actually do?
- Is it safe for my environment?
- Do I have a recent backup?
- Should I test on a throwaway database first?

## The 3-Hour Recovery Process

### Step 1: Don't Panic (Easier Said Than Done)

**First instinct:** "Can I undo this?!"

**Reality check:**

- ❌ PostgreSQL has no "undo" button
- ❌ `DROP SCHEMA CASCADE` is permanent
- ❌ No database transaction to rollback
- ✅ I **did** have backups (thank god)

### Step 2: Find the Most Recent Backup

```bash
# apps/strapi/backups/
ls -lt *.tar.gz | head -5
```

**Found:**

- `pre-config-import-backup-20251201-185738.tar.gz` (1 day old)
- `post-migration-backup-20251125-143022.tar.gz` (1 week old)

**Decision:** Use the 1-day-old backup. Acceptable data loss: ~8 hours of work (much better than 30 hours).

### Step 3: Strapi Import to the Rescue

Strapi's export/import feature saved me:

```bash
# Extract backup
cd apps/strapi/backups
tar -xzf pre-config-import-backup-20251201-185738.tar.gz

# Import into Strapi (database running)
cd ../../
yarn strapi import -f backups/strapi-export-20251201-185738/export_*.tar.gz.enc
```

**Results (3 hours later):**

```
✔ entities: 203 transferred (size: 253 KB)
✔ assets: 331 transferred (size: 27.4 MB)
✔ links: 355 transferred (size: 68.5 KB)
✔ configuration: 91 transferred (size: 221.6 KB)

Restored Content:
├── 10 pages (all pages recovered)
├── 331 media assets (all images back)
├── 1 navbar (fully restored)
├── 1 footer (fully restored)
└── All locales, permissions, and settings
```

**Data Loss:** ~8 hours of recent edits (acceptable vs 30 hours total loss).

## Building Safe Seed Scripts (The Right Way)

After recovery, I built **environment-specific seed scripts** that can't delete your data.

### The Safe Pattern: Check-Then-Update

**Destructive Approach (CI only):**

```typescript
// ❌ DANGEROUS for development
await strapi.db.query('api::page.page').deleteMany({});
await strapi.db.query('api::page.page').create({ data: { ... } });
```

**Safe Approach (Development):**

```typescript
// ✅ SAFE: Update if exists, create if not
const existingPage = await strapi.documents("api::page.page").findMany({
  filters: { slug: "e2e-test-page" },
})

if (existingPage.length > 0) {
  // Update existing
  await strapi.documents("api::page.page").update({
    documentId: existingPage[0].documentId,
    data: { title: "E2E Test Page" /* ... */ },
  })
} else {
  // Create new
  await strapi.documents("api::page.page").create({
    data: { title: "E2E Test Page" /* ... */ },
  })
}
```

### Environment Detection

Add environment checks to your scripts:

```typescript
// Check environment before destructive operations
const isDevelopment = process.env.NODE_ENV === "development"
const isCI = process.env.CI === "true"

if (isDevelopment && !isCI) {
  console.log("🛡️  Running SAFE seed (preserving existing data)")
  await safeSeeding()
} else {
  console.log("⚠️  Running DESTRUCTIVE seed (CI environment)")
  await destructiveSeeding()
}
```

### Clear Script Naming

```bash
# Old (ambiguous)
yarn seed:e2e          # Is this safe? Who knows!

# New (explicit)
yarn seed:e2e          # CI only - DESTRUCTIVE
yarn seed:e2e:safe     # Development - SAFE
```

## The New Safe Seed Architecture

I created three new files:

### 1. Safe Seed Runner (`scripts/seed-e2e-data-safe.sh`)

```bash
#!/bin/bash
# SAFE FOR DEVELOPMENT - Does NOT delete existing data

echo "🛡️  Running SAFE E2E seed (preserving existing content)..."
node scripts/run-seed-safe.js
```

### 2. Strapi Bootstrap (`scripts/run-seed-safe.js`)

```javascript
const strapi = require("@strapi/strapi")

async function main() {
  const app = await strapi({ distDir: "./dist" }).load()

  // Import safe seed function
  const { seedE2EDataSafe } = require("../database/seeds/e2e-test-data-safe")
  await seedE2EDataSafe(strapi)

  await app.destroy()
  console.log("✅ Safe seeding complete!")
}

main()
```

### 3. Safe Seed Logic (`database/seeds/e2e-test-data-safe.ts`)

```typescript
export async function seedE2EDataSafe(strapi: any) {
  console.log("Checking for existing E2E test page...")

  const existingPages = await strapi.documents("api::page.page").findMany({
    filters: { slug: "e2e-test-page" },
  })

  if (existingPages.length > 0) {
    console.log("✅ E2E page exists. Updating...")
    await strapi.documents("api::page.page").update({
      documentId: existingPages[0].documentId,
      data: {
        title: "E2E Test Page",
        slug: "e2e-test-page",
        // ... rest of test data
      },
    })
  } else {
    console.log("➕ Creating new E2E test page...")
    await strapi.documents("api::page.page").create({
      data: {
        title: "E2E Test Page",
        slug: "e2e-test-page",
        // ... rest of test data
      },
    })
  }

  console.log("✅ E2E seed data ready (existing content preserved)")
}
```

## Prevention Checklist

Here's what I do now **before running any database script**:

### ✅ Pre-Flight Checklist

- [ ] **Check script contents** (`cat scripts/seed-e2e-data.sh`)
  - Does it contain `DROP SCHEMA`?
  - Does it contain `deleteMany()`?
  - Does it say "CI ONLY"?
- [ ] **Verify recent backup exists** (`ls -lt backups/ | head -1`)
  - Is the backup less than 24 hours old?
  - Can I afford to lose changes since then?
- [ ] **Confirm environment**
  - Am I in CI or local development?
  - Does the script match my environment?
- [ ] **Test on throwaway database first**
  - Create a copy: `createdb strapi_test_copy`
  - Run script against copy
  - Verify behavior before running on dev database

### 🚫 Red Flags (Stop Immediately)

**If you see ANY of these, STOP and investigate:**

1. `DROP SCHEMA CASCADE` in a script
2. `deleteMany({})` with no filters (deletes everything)
3. `TRUNCATE TABLE` commands
4. "CI ONLY" warnings in comments
5. Script names like `reset-database.sh` or `clean-db.sh`

## Key Takeaways

### What I Learned

1. **Environment matters more than you think**

   - CI scripts ≠ development scripts
   - Throwaway databases ≠ databases with real content
   - Same operation, drastically different consequences

2. **Backups are your safety net**

   - Daily automated backups saved me
   - Manual backups before risky operations
   - Test restore process (know it works!)

3. **Defensive programming saves careers**

   - Add confirmation prompts for destructive ops
   - Detect environment and adjust behavior
   - Provide SAFE and DESTRUCTIVE versions

4. **Read scripts before running them**
   - One minute of reading > 3 hours of recovery
   - Check for `DROP`, `DELETE`, `TRUNCATE`
   - Verify script matches your intent

### What You Can Do Right Now

**5-Minute Safety Checklist:**

1. **Review your seed scripts** (`grep -r "DROP SCHEMA" .`)
2. **Check last backup** (`ls -lt backups/`)
3. **Test restore process** (can you actually restore?)
4. **Add environment detection** to destructive scripts
5. **Document which scripts are safe** for development
