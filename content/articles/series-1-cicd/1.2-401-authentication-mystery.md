## The Mystery: "It Works on My Machine"

**Friday, 3:47 PM.** I pushed what I thought was a simple fix to our contact form. GitHub Actions kicked off, and I watched the CI pipeline run...

```
✅ Lint
✅ Type check
✅ Build
❌ E2E tests - FAILED
```

"Strange," I thought. "E2E tests passed locally just 5 minutes ago."

I clicked into the logs:

```bash
Error: page.goto: net::ERR_HTTP_401
  at http://localhost:3000/contact

API Request failed: 401 Unauthorized
GET http://localhost:1337/api/pages?filters[fullPath][$eq]=/contact
```

Every. Single. API request. **401 Unauthorized.**

**Local environment:** 100% passing (69/69 tests)  
**CI environment:** 100% failing (0/69 tests)  
**Time wasted over the next 6 hours:** Priceless 😅

This is the complete debugging journey—the wrong hypotheses, the dead ends, and the two distinct root causes that took 6 hours to uncover.

---

## Part 1: The First Hypothesis (Wrong, but Logical)

### Theory: "The API token isn't in CI secrets"

**Time spent:** 30 minutes

The 401 error screamed "authentication problem," so naturally I checked the GitHub Actions secrets:

```yaml
# .github/workflows/e2e-tests.yml
env:
  STRAPI_REST_READONLY_API_KEY: ${{ secrets.STRAPI_API_KEY }}
```

"Okay, secret is set in the workflow. Let me verify it's actually available..."

```yaml
steps:
  - name: Debug - Check if API key exists
    run: |
      if [ -z "$STRAPI_REST_READONLY_API_KEY" ]; then
        echo "❌ API key is EMPTY"
      else
        echo "✅ API key exists (length: ${#STRAPI_REST_READONLY_API_KEY})"
      fi
```

**CI output:**

```
✅ API key exists (length: 64)
```

"The secret is there. What's next?"

**Dead end #1:** Secret was properly configured. The problem wasn't about secret availability.

## Part 2: The Second Hypothesis (Getting Warmer)

### Theory: "The token isn't reaching the Next.js application"

**Time spent:** 1 hour

I know Next.js needs environment variables in `.env.local` to use them at runtime. Let me check if CI is creating that file:

```yaml
steps:
  - name: Prepare environment variables
```

**CI output:**

```
Checking apps/ui/.env.local contents...
STRAPI_REST_READONLY_API_KEY=1234567890abcdef...
```

"Environment file is created correctly. Token is definitely there."

I added more debugging to the Next.js application itself:

```typescript
// apps/ui/src/lib/strapi.ts
export function createStrapiClient() {
  const token = process.env.STRAPI_REST_READONLY_API_KEY
```

**CI output:**

"Wait... WHAT?! The token exists in `.env.local` but Next.js says it's undefined?!"

**Breakthrough insight #1:** The token exists in the file system but isn't being read by the Next.js process.

**But why?**

## Part 3: The Workflow Timing Revelation

### Theory: "When is the environment file being created relative to the build?"

**Time spent:** 2 hours

Let me look at the **order** of steps in the GitHub Actions workflow:

```yaml
# ❌ WRONG ORDER (what I had)
steps:
  - name: Install dependencies
    run: yarn install

  - name: Build UI
    run: yarn workspace @repo/ui build

  - name: Prepare environment variables # ⚠️ Too late!
    run: |
      echo "STRAPI_REST_READONLY_API_KEY=${{ secrets.STRAPI_API_KEY }}" >> apps/ui/.env.local

  - name: Start UI
    run: yarn workspace @repo/ui start

  - name: Run E2E tests
    run: yarn test:e2e
```

"Oh no..."

The `.env.local` file is created **AFTER** the build step. But here's what I learned about Next.js:

### Next.js SSR Data Fetching Happens at BUILD Time

Next.js has Server-Side Rendering (SSR) routes that fetch data during the build process to generate static pages:

```typescript
// app/contact/page.tsx
export default async function ContactPage() {
  // This runs during 'yarn build', not at runtime!
  const page = await getPageBySlug('contact');

  return <Page data={page} />;
}
```

When Next.js builds the contact page, it:

1. Calls `getPageBySlug('contact')`
2. That function uses `createStrapiClient()`
3. The client needs `process.env.STRAPI_REST_READONLY_API_KEY`
4. **But the env file doesn't exist yet!**

**Build-time flow (WRONG order):**

```
yarn build
  → Compile /contact page
  → Call getPageBySlug()
  → Read process.env.STRAPI_REST_READONLY_API_KEY
  → undefined ❌
  → Build succeeds (with undefined token)

(Later) Create .env.local file

yarn start
  → Runtime API calls use undefined token
  → 401 Unauthorized ❌
```

### The Fix: Move Environment Setup BEFORE Build

```yaml
# ✅ CORRECT ORDER
steps:
  - name: Install dependencies
    run: yarn install

  - name: Prepare environment variables # 🎯 Before build!
    run: |
      echo "STRAPI_REST_READONLY_API_KEY=${{ secrets.STRAPI_API_KEY }}" >> apps/ui/.env.local
      echo "DATABASE_PASSWORD=${{ secrets.DATABASE_PASSWORD }}" >> apps/strapi/.env

  - name: Build UI
    run: yarn workspace @repo/ui build

  - name: Start UI
    run: yarn workspace @repo/ui start

  - name: Run E2E tests
    run: yarn test:e2e
```

"This should fix it!"

I pushed the change (commit `c0a0a0e`), waited for CI...

```
✅ Lint
✅ Type check
✅ Build
❌ E2E tests - STILL FAILING
```

"STILL 401 errors?! But the token is there at build time now!"

**Time elapsed:** 3.5 hours. **Progress:** Marginal.

## Part 4: The Second Root Cause (SHA512 Hashing)

### The Clue: Different Behavior in Fresh vs Existing Databases

**Time spent:** 2.5 hours

I started noticing a pattern:

- **Local development** (existing database): ✅ Authentication works
- **CI environment** (fresh database): ❌ 401 Unauthorized

"What's different between my local database and CI's fresh database?"

### Digging into Strapi's Source Code

I opened Strapi's authentication middleware and found this:

```javascript
// @strapi/plugin-users-permissions/server/services/jwt.js
const verify = (token) => {
  return new Promise((resolve, reject) => {
    // Strapi stores tokens as SHA512 hashes, not plaintext!
    const hashedToken = crypto.createHash("sha512").update(token).digest("hex")

    // Compare hashed version
    const validToken = database.findOne({
      where: { accessKey: hashedToken },
    })

    if (!validToken) {
      return reject(new Error("Invalid token"))
    }

    resolve(validToken)
  })
}
```

"Wait... Strapi stores tokens as SHA512 hashes?!"

Let me check my seed script:

```typescript
// ❌ WRONG - Storing plaintext token
await strapi.db.query("admin::api-token").create({
  data: {
    name: "E2E Test Token",
    accessKey: process.env.STRAPI_REST_READONLY_API_KEY, // Plaintext!
    type: "read-only",
  },
})
```

### The Authentication Flow (Why It Failed)

**Fresh database (CI):**

```
1. Seed script runs:
   → Stores plaintext token "abcd1234..." in database

2. API request arrives with token "abcd1234..."
   → Strapi hashes it: SHA512("abcd1234...") = "xyz789..."
   → Database lookup for "xyz789..." (the hash)
   → No match! (database has plaintext "abcd1234...")
   → 401 Unauthorized ❌
```

**Existing database (local):**

```
1. Created token via Strapi admin UI (manually)
   → Strapi automatically hashed it and stored hash

2. API request arrives with token
   → Strapi hashes it: SHA512(token) = hash
   → Database lookup for hash
   → Match! ✅
```

### The Fix: Hash Tokens in Seed Script

```typescript
// ✅ CORRECT - Hash token before storing
import crypto from "crypto"

const apiToken = process.env.STRAPI_REST_READONLY_API_KEY

// Hash the token the same way Strapi does internally
const hashedToken = crypto.createHash("sha512").update(apiToken).digest("hex")

await strapi.db.query("admin::api-token").create({
  data: {
    name: "E2E Test Token",
    accessKey: hashedToken, // Hashed version!
    type: "read-only",
    lifespan: null,
    expiresAt: null,
    createdAt: new Date(),
    updatedAt: new Date(),
  },
})
```

```

✅ Type check
✅ Build
✅ E2E tests - 69/69 PASSING! 🎉
```

## The Complete Solution: Two Fixes Required

### Fix #1: Set Environment Variables BEFORE Build

**Problem:** Next.js SSR routes need API tokens during build time, not just runtime.

**Solution:** Move environment variable setup before the build step.

```yaml
# .github/workflows/ci.yml
steps:
  - uses: actions/checkout@v4

  - name: Setup Node.js
    uses: actions/setup-node@v4
    with:
      node-version: "20"
      cache: "yarn"

  - name: Install dependencies
    run: yarn install --frozen-lockfile

  # 🎯 Critical: Set env vars BEFORE build
  - name: Prepare environment variables
    run: |
      echo "STRAPI_REST_READONLY_API_KEY=${{ secrets.STRAPI_API_KEY }}" >> apps/ui/.env.local
      echo "DATABASE_PASSWORD=${{ secrets.DATABASE_PASSWORD }}" >> apps/strapi/.env

  - name: Build Next.js
    run: yarn workspace @repo/ui build

  # Now runtime has access to env vars too
  - name: Start Next.js
    run: yarn workspace @repo/ui start &

  - name: Run E2E tests
    run: yarn test:e2e
```

### Fix #2: Hash API Tokens with SHA512

**Problem:** Strapi stores API tokens as SHA512 hashes. Seed scripts must match this format.

**Solution:** Hash tokens before inserting into database.

```typescript
// apps/strapi/database/seeds/e2e-test-data.ts
import crypto from "crypto"

export default async ({ strapi }) => {
  console.log("🌱 Seeding E2E test data...")

  // Get token from environment
  const apiToken = process.env.STRAPI_REST_READONLY_API_KEY

  if (!apiToken) {
    throw new Error("STRAPI_REST_READONLY_API_KEY not set")
  }

  // Hash it the same way Strapi does internally
  const hashedToken = crypto.createHash("sha512").update(apiToken).digest("hex")

  console.log("🔐 Token hashed for storage")

  // Store hashed version
  await strapi.db.query("admin::api-token").create({
    data: {
      name: "E2E Test Read-Only Token",
      description: "Token for E2E tests (read-only access)",
      type: "read-only",
      accessKey: hashedToken, // SHA512 hash, not plaintext
      lifespan: null, // No expiration
      expiresAt: null,
      createdAt: new Date(),
      updatedAt: new Date(),
    },
  })

  console.log("✅ API token seeded")
}
```

**Verification test:**

```typescript
// Verify token works
const response = await fetch("http://localhost:1337/api/pages", {
  headers: {
    Authorization: `Bearer ${process.env.STRAPI_REST_READONLY_API_KEY}`,
  },
})

if (response.status === 401) {
  console.error("❌ Token authentication failed")
} else {
  console.log("✅ Token authentication successful")
}
```

## Lessons Learned (The Hard Way)

### 1. Next.js SSR = Build-Time Data Fetching

**Key insight:** Next.js Server-Side Rendering fetches data during `yarn build`, not just at runtime.

**Implication:** Environment variables needed for SSR **must exist before the build step**.

**Applies to all SSR frameworks:**

- Next.js (React)
- Nuxt (Vue)
- SvelteKit (Svelte)
- Remix (React)

**Workflow pattern:**

```
1. Checkout code
2. Install dependencies
3. Set environment variables ← BEFORE build!
4. Build application
5. Run tests/deploy
```

---

### 2. Hash Format Matters (A LOT)

**Key insight:** When a system stores hashes, seed data must match the hashing algorithm.

**Strapi specifics:**

- API tokens stored as **SHA512 hashes**
- Uses Node.js `crypto.createHash('sha512')`
- Seed scripts must hash tokens identically

**General principle:**

```
If production uses hashed storage
  → Development/CI must also use hashed storage
  → Otherwise authentication fails in fresh environments
```

---

### 3. Local vs CI Parity Requires More Than "Same Code"

**What I learned:**

- ✅ Same codebase
- ✅ Same environment variables
- ❌ **Different database states** (local has manual tokens, CI has seeded tokens)
- ❌ **Different workflow timing** (local always has .env.local, CI creates it mid-workflow)

**Achieving true parity:**

1. **Database seeding** must match production data format (hashing, encoding, etc.)
2. **Workflow timing** must mirror local development (env vars before build)
3. **Test both paths:** manual setup (local) AND automated setup (CI)

---

### 4. Debug Systematically, Not Randomly

**What worked:**

1. ✅ Add logging at each step (token exists? token value? token length?)
2. ✅ Isolate variables (is it secrets? env file? build timing? hashing?)
3. ✅ Compare working vs failing (local vs CI, fresh vs existing DB)
4. ✅ Read source code (Strapi's authentication internals revealed SHA512)

**What didn't work:**

1. ❌ Guessing solutions and hoping ("Maybe restart Docker?")
2. ❌ Changing multiple things at once (can't tell what fixed it)
3. ❌ Assuming "it works locally" means CI should work
