## The Problem: "It Works Locally, Fails in CI"

You've seen this before:

```bash
# Local development
yarn build
✅ Success - all SSR routes compiled

# GitHub Actions CI
yarn build
❌ Error: STRAPI_REST_READONLY_API_KEY is not defined
```

Your environment variables are set in the workflow. You triple-checked the secrets configuration. The build step runs successfully. But somehow, your API calls return 401 Unauthorized.

**What's happening?**

---

## The Root Cause: Build-Time vs Runtime

Most developers think environment variables are "runtime configuration." But with Server-Side Rendering (SSR), that's only half the story.

### How Next.js SSR Works

When you build a Next.js app with SSR routes, here's what happens:

```javascript
// app/blog/[slug]/page.tsx
export default async function BlogPost({ params }) {
  // This runs at BUILD TIME, not just at runtime!
  const response = await fetch(
    `${process.env.NEXT_PUBLIC_STRAPI_URL}/api/articles/${params.slug}`,
    {
      headers: {
        Authorization: `Bearer ${process.env.STRAPI_REST_READONLY_API_KEY}`, // ← Needs to exist NOW
      },
    }
  )

  const article = await response.json()
  return <Article data={article} />
}
```

**What Next.js does during `yarn build`:**

1. ✅ Compiles TypeScript → JavaScript
2. ✅ Bundles client-side code
3. ✅ **Pre-renders SSR routes** (calls `fetch` in your code!)
4. ✅ Generates static HTML for pages

If `STRAPI_REST_READONLY_API_KEY` isn't available during step 3, your code runs with `undefined`, and the API call fails.

## The Wrong Workflow Order

Here's what our GitHub Actions workflow looked like **before** the fix:

```yaml
# ❌ WRONG: Environment variables set AFTER build
jobs:
  build:
    name: Build all apps
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4

      - name: Install dependencies
        run: yarn --frozen-lockfile

      - name: Build UI
        run: yarn workspace @repo/ui build # ← SSR runs here, no token!

      - name: Prepare Environment Variables # ← Token set here (too late!)
        run: |
          cp apps/ui/.env.local.example apps/ui/.env.local
          echo "STRAPI_REST_READONLY_API_KEY=${{ env.STRAPI_REST_READONLY_API_KEY }}" >> apps/ui/.env.local

      - name: Run E2E tests
        run: yarn test:e2e # Tests fail with 401 because build had no token
```

**The flow:**

1. Build runs → SSR routes execute `fetch` → `process.env.STRAPI_REST_READONLY_API_KEY` is `undefined`
2. Build "succeeds" (TypeScript compiles, bundle created)
3. Environment file created with token (too late - build already done)
4. Tests run → SSR routes still have `undefined` from build → 401 errors

**Result:** 100% CI failures with cryptic 401 Unauthorized errors

---

## The Correct Workflow Order

Here's the fix - move environment setup **before** the build:

```yaml
# ✅ CORRECT: Environment variables set BEFORE build
jobs:
  build:
    name: Build all apps
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4

      - name: Install dependencies
        run: yarn --frozen-lockfile

      - name: Prepare Environment Variables # ← Moved BEFORE build!
        run: |
          cp apps/ui/.env.local.example apps/ui/.env.local
          echo "STRAPI_REST_READONLY_API_KEY=${{ env.STRAPI_REST_READONLY_API_KEY }}" >> apps/ui/.env.local

      - name: Build UI
        run: yarn workspace @repo/ui build # ← SSR has token now!

      - name: Run E2E tests
        run: yarn test:e2e # Tests pass - SSR routes compiled correctly
```

**The flow:**

1. Environment file created with API token
2. Build runs → SSR routes execute `fetch` → `process.env.STRAPI_REST_READONLY_API_KEY` has value ✅
3. Build succeeds with correctly authenticated API calls
4. Tests run → SSR routes work perfectly → 100% success

**Result:** 100% CI success rate, SSR routes authenticate correctly

## Why This Isn't Obvious

### Mental Model Mismatch

Developers think of environment variables as "runtime config":

- Server starts → reads `.env` file → serves requests

But with SSR frameworks, environment variables are **build-time dependencies** too:

- **Build starts** → reads `.env` file → **pre-renders pages** → generates static files

### Local Development Hides the Problem

On your local machine:

```bash
# You always have .env.local before building
touch apps/ui/.env.local  # Created once
yarn build                # Always has access to env vars
```

In CI, each run starts fresh:

```bash
# CI has no .env.local unless you create it
yarn build                # If .env.local missing = undefined vars
```

The mismatch between local (persistent `.env.local`) and CI (ephemeral environment) hides the dependency ordering issue.

---

## Framework-Agnostic Principle

This isn't just a Next.js problem. **Any SSR framework** that pre-renders at build time needs environment variables during the build:

### Nuxt.js (Vue)

```javascript
// nuxt.config.ts
export default defineNuxtConfig({
  runtimeConfig: {
    apiSecret: process.env.API_SECRET, // ← Needs to exist at build time
  },
})
```

### SvelteKit

```javascript
// src/routes/+page.server.ts
export async function load() {
  const response = await fetch(process.env.API_URL) // ← Build-time fetch
  return { data: await response.json() }
}
```

### Remix

```typescript
// app/routes/index.tsx
export async function loader() {
  const data = await fetch(process.env.API_ENDPOINT) // ← Build-time loader
  return json(data)
}
```

**Universal rule:** If your framework pre-renders pages during build, environment variables must be available **before** the build step.

## Decision Framework: When to Set Env Vars

Use this framework to determine environment variable timing in your CI/CD workflow:

| Scenario                                | Set Before Build? | Reasoning                                                        |
| --------------------------------------- | ----------------- | ---------------------------------------------------------------- |
| **SSR data fetching**                   | ✅ Yes            | Build-time pre-rendering needs API access                        |
| **Build-time feature flags**            | ✅ Yes            | Code splitting decisions happen during build                     |
| **API endpoints for static generation** | ✅ Yes            | Static pages fetch data during build                             |
| **Runtime-only API calls**              | ⚠️ Either         | Works both ways, but "before" matches local development          |
| **Client-side only variables**          | ⚠️ Either         | No build-time dependency, but consistency helps                  |
| **Production secrets**                  | ❌ No             | Keep secrets out of build artifacts when possible                |
| **Database connection strings**         | ✅ Yes            | ORMs and seed scripts may run during build or before build steps |

**Best practice:** When in doubt, set environment variables **before** the build. It mirrors local development and prevents unexpected `undefined` errors.

## Debugging Checklist

If you're seeing `undefined` environment variables or 401 errors in CI:

1. **Check workflow order:**

   ```bash
   # Does env setup come BEFORE build?
   git log --oneline -- .github/workflows/*.yml
   ```

2. **Verify build logs:**

   ```bash
   # Look for "Building page: /blog/[slug]" or similar
   # If present, those pages run fetch() during build
   ```

3. **Test locally with fresh environment:**

   ```bash
   rm apps/ui/.env.local     # Delete local env
   yarn build                # Does it fail like CI?
   ```

4. **Confirm SSR vs CSR:**
   - SSR (Server-Side Rendering): Needs env vars at build time
   - CSR (Client-Side Rendering): Needs env vars at runtime only
   - Static Generation (SSG): Needs env vars at build time

## Key Takeaways

1. **SSR frameworks execute code during build, not just at runtime**

   - `fetch()` calls in SSR routes run during `yarn build`
   - Environment variables must exist before build starts

2. **CI workflow order must match local development mental model**

   - Locally: `.env.local` exists before every build
   - CI: Must create `.env.local` **before** build step

3. **This applies to all SSR frameworks**

   - Next.js, Nuxt, SvelteKit, Remix - same principle
   - If it pre-renders, it needs env vars at build time

4. **When in doubt, set env vars before build**
   - Matches local development
   - Prevents `undefined` surprises
   - Enables build-time feature flags and optimization
