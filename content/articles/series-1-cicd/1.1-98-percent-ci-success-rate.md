## The Problem: Flaky CI Pipelines Cost Time and Trust

Every developer knows the pain. You push code, CI runs for 10 minutes, and fails on something that worked perfectly on your machine. You restart the workflow. It passes. What changed? Nothing. That's a **flaky build**.

Industry data shows the average CI/CD success rate hovers around **85%**. That means **1 in 7 builds fails** for reasons unrelated to code quality—timing issues, network blips, resource contention, or service startup race conditions.

**The real cost:**

- **10-15 wasted minutes** per false failure (context switching, investigation, restart)
- **Developer trust erosion** ("Is this a real bug or just CI being flaky?")
- **Delayed deployments** (can't ship if you don't trust green builds)
- **Meeting overhead** (discussions about why CI failed... again)

I built a CI/CD pipeline for a full-stack monorepo (Next.js + Strapi + PostgreSQL) that achieves **98% success rate**. Here's how.

## Strategy 1: Path-Based Triggering (50% Fewer Runs)

### The Problem

Default GitHub Actions triggers run on **every push** to **every branch**. In a monorepo, that means:

- Frontend change → runs frontend tests ✅ AND backend tests ❌ (unnecessary)
- Docs update → runs full test suite ❌ (wasteful)
- Dependency update → runs everything ⚠️ (sometimes needed)

**Result:** 50% of CI runs tested code that didn't change.

### The Solution

GitHub Actions supports `paths` filters to run workflows only when specific files change:

```yaml
# .github/workflows/ci.yml

name: CI Pipeline

on:
  push:
    branches: [main, develop]
    paths:
      # Run if application code changes
      - "apps/**"
      - "packages/**"
      # Run if CI config itself changes
      - ".github/workflows/**"
      # Run if dependencies change
      - "package.json"
      - "yarn.lock"
      # SKIP if only docs change
      - "!docs/**"
      - "!**.md"

  pull_request:
    branches: [main, develop]
    paths:
      - "apps/**"
      - "packages/**"
      - ".github/workflows/**"
      - "package.json"
      - "yarn.lock"

jobs:
  test:
    runs-on: ubuntu-latest
    # ... rest of workflow
```

**Key patterns:**

- `apps/**` - Any file in apps/ directory triggers CI
- `!docs/**` - Exclude docs changes (prefix `!` means ignore)
- `**.md` - Any Markdown file at any level
- Multiple path filters = OR logic (any match triggers)

### The Results

**Before path filtering:**

- 200 pushes/month → 200 CI runs
- ~50% tested unchanged code
- 20 hours GitHub Actions minutes/month

**After path filtering:**

- 200 pushes/month → 100 CI runs (50% reduction)
- 100% of runs test relevant code
- 10 hours GitHub Actions minutes/month (50% cost savings)

**Developer impact:**

- Faster feedback (fewer jobs in queue)
- Less notification noise (only relevant failures)
- More confident in CI purpose (every run matters)

## Strategy 2: Turborepo Caching (50% Faster Builds)

### The Problem

In a monorepo, **incremental changes** are common:

- Fix a bug in the frontend → rebuild frontend ✅, rebuild backend ❌ (unchanged)
- Update a shared util → rebuild apps using it ✅, rebuild unrelated apps ❌

**Traditional CI rebuilds everything every time.** In my monorepo:

- `yarn build` takes 8-12 minutes (Next.js + Strapi + TypeScript compilation)
- 80% of builds only changed 1-2 packages
- Wasted 6-9 minutes rebuilding unchanged code

### The Solution

Turborepo provides **task caching** with content-based hashing:

```yaml
# .github/workflows/ci.yml

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: "20"
          cache: "yarn"

      # Turborepo cache restoration
      - name: Setup Turborepo cache
        uses: actions/cache@v3
        with:
          path: .turbo
          key: ${{ runner.os }}-turbo-${{ github.sha }}
          restore-keys: |
            ${{ runner.os }}-turbo-

      - name: Install dependencies
        run: yarn install --frozen-lockfile

      # Turbo runs tasks, uses cache for unchanged packages
      - name: Build all packages
        run: yarn build

      - name: Run tests
        run: yarn test
```

**How Turborepo caching works:**

1. **Hash inputs:** Source files, dependencies, config files
2. **Check cache:** Has this exact input hash been built before?
3. **Cache hit:** Restore outputs (build artifacts, test results), skip task
4. **Cache miss:** Run task, store outputs for future runs

**Configuration:**

```json
// turbo.json
{
  "pipeline": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": [".next/**", "dist/**", ".strapi/**"],
      "cache": true
    },
    "test": {
      "dependsOn": ["build"],
      "outputs": ["coverage/**"],
      "cache": true
    },
    "lint": {
      "outputs": [],
      "cache": true
    }
  }
}
```

### The Results

**Before Turborepo caching:**

- Every CI run: 8-12 minutes (full rebuild)
- 200 builds/month × 10 min avg = 2,000 minutes/month
- No benefit from previous builds

**After Turborepo caching:**

- Cache hit (80% of runs): 4-5 minutes (only changed packages)
- Cache miss (20% of runs): 8-12 minutes (same as before)
- 200 builds/month × 5.2 min avg = 1,040 minutes/month (48% reduction)

**Developer impact:**

- Faster PR feedback (4-5 min typical vs 10 min worst case)
- Fewer "waiting for CI" complaints
- Local development benefits too (Turbo cache works locally)

## Strategy 3: Parallel Execution (3x Faster Feedback)

### The Problem

Running tests sequentially is **safe but slow**:

```yaml
# Sequential (slow)
jobs:
  build-and-test:
    steps:
      - Lint (2 min)
      - Type check (3 min)
      - Unit tests (4 min)
      - Build (5 min)
      - E2E tests (8 min)
      - Lighthouse (3 min)
    # Total: 25 minutes 😱
```

### The Solution

GitHub Actions supports **parallel jobs** that run simultaneously:

```yaml
# .github/workflows/ci.yml

jobs:
  # Quick checks (run first for fast feedback)
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: yarn install
      - run: yarn lint
      # Completes in ~2 minutes

  type-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: yarn install
      - run: yarn type-check
      # Completes in ~3 minutes

  # Longer tests (run in parallel with quick checks)
  unit-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: yarn install
      - run: yarn test
      # Completes in ~4 minutes

  # Build required for E2E tests
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: yarn install
      - run: yarn build
      - uses: actions/upload-artifact@v3
        with:
          name: build-output
          path: |
            apps/ui/.next
            apps/strapi/.strapi

  # E2E tests depend on build
  e2e-tests:
    needs: build
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:17
        env:
          POSTGRES_DB: strapi_test
          POSTGRES_USER: strapi_user
          POSTGRES_PASSWORD: ${{ secrets.DATABASE_PASSWORD }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/download-artifact@v3
        with:
          name: build-output
      - run: yarn install
      - run: yarn test:e2e
      # Completes in ~8 minutes

  # Lighthouse (can run in parallel with E2E)
  lighthouse:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/download-artifact@v3
        with:
          name: build-output
      - run: yarn lighthouse
      # Completes in ~3 minutes
```

**Job dependency graph:**

```
lint ─────┐
          ├─> (all parallel, ~4 min max)
type-check┤
          │
unit-tests┘

     ↓ (when any fail, stop here)

build ────┐
          ├─> e2e-tests ──┐
          │               ├─> (parallel, ~8 min max)
          └─> lighthouse ─┘

Total pipeline: ~12 minutes (vs 25 sequential)
```

### The Results

**Before parallelization:**

- Sequential execution: 25 minutes
- Single failure point: any job fails → no visibility into other jobs
- Slow feedback: wait 25 min to see if last job passes

**After parallelization:**

- Parallel execution: 12 minutes (52% faster)
- Multiple failure visibility: see lint, type, and test failures simultaneously
- Fast feedback: know about lint errors in 2 minutes (don't wait for E2E)

**Developer impact:**

- Fix quick issues first (lint failures visible in 2 min)
- Parallel development (team members don't block each other in queue)
- Psychological win (12 min feels much faster than 25 min)

## Strategy 4: Health Check Polling (100% Reliability)

### The Problem

E2E tests require **services to be ready**:

- PostgreSQL must accept connections
- Strapi API must respond to requests
- Next.js server must serve pages

**Traditional approach:**

```yaml
steps:
  - name: Start PostgreSQL
    run: docker-compose up -d postgres

  - name: Wait for PostgreSQL
    run: sleep 10 # Hope 10 seconds enough? 🤞

  - name: Start Strapi
    run: yarn workspace @repo/strapi dev &

  - name: Wait for Strapi
    run: sleep 30 # Hope 30 seconds enough? 🤞🤞

  - name: Run E2E tests
    run: yarn test:e2e
    # 20% failure rate from services not ready 😱
```

**Problems:**

- **Fast runners:** Waste 20+ seconds waiting unnecessarily
- **Slow runners:** 40 seconds not enough, tests fail with connection errors
- **Flaky builds:** Sometimes works, sometimes doesn't (timing-dependent)

### The Solution

**HTTP health check polling** with exponential backoff:

```yaml
steps:
  - name: Start PostgreSQL
    run: docker-compose up -d postgres

  - name: Wait for PostgreSQL (health check)
    run: |
      until pg_isready -h localhost -U strapi_user; do
        echo "Waiting for PostgreSQL..."
        sleep 2
      done
      echo "PostgreSQL ready!"
    timeout-minutes: 2

  - name: Prepare environment variables
    run: |
      echo "STRAPI_REST_READONLY_API_KEY=${{ secrets.STRAPI_API_KEY }}" >> apps/ui/.env.local
      echo "DATABASE_PASSWORD=${{ secrets.DATABASE_PASSWORD }}" >> apps/strapi/.env

  - name: Start Strapi
    run: |
      cd apps/strapi
      yarn develop &
      STRAPI_PID=$!
      echo "Strapi started with PID $STRAPI_PID"

  - name: Wait for Strapi (health check)
    run: |
      ATTEMPTS=0
      MAX_ATTEMPTS=60

      until curl -f http://localhost:1337/admin > /dev/null 2>&1; do
        ATTEMPTS=$((ATTEMPTS + 1))
        if [ $ATTEMPTS -ge $MAX_ATTEMPTS ]; then
          echo "Strapi failed to start after $MAX_ATTEMPTS attempts"
          exit 1
        fi
        
        if [ $((ATTEMPTS % 10)) -eq 0 ]; then
          echo "Still waiting for Strapi... (attempt $ATTEMPTS/$MAX_ATTEMPTS)"
        fi
        
        sleep 2
      done

      echo "Strapi ready after $ATTEMPTS attempts!"
    timeout-minutes: 2

  - name: Run E2E tests
    run: yarn test:e2e
```

**Health check pattern:**

1. **Make health request** (HTTP GET or database query)
2. **Check response** (200 OK = ready, connection refused = not ready)
3. **If not ready:** Wait interval (2 seconds), increment attempt counter, retry
4. **If ready:** Proceed to next step
5. **If max attempts exceeded:** Fail with clear error message

### The Results

**Before health checks:**

- Fixed sleeps: 40 seconds average
- Success rate: 80% (20% timeout-related failures)
- Developer frustration: High ("Why did CI fail when code is fine?")

**After health checks:**

- Adaptive waiting: 8-25 seconds average (depends on runner speed)
- Success rate: 100% (0% timeout-related failures)
- Developer trust: High ("If CI passes, it's really working")

**Key insight:** Health checks cost nothing when services are fast, but save you when runners are slow.

## Common Pitfalls to Avoid

### ❌ Pitfall 1: Testing Everything on Every Push

**Mistake:** Running full test suite on docs-only changes.

**Fix:** Use `paths` filters to skip CI when only non-code files change.

```yaml
on:
  push:
    paths:
      - "!docs/**"
      - "!**.md"
```

---

### ❌ Pitfall 2: Sequential Jobs When Parallelization Possible

**Mistake:** Running lint → type-check → test sequentially when they have no dependencies.

**Fix:** Define independent jobs that run in parallel.

```yaml
jobs:
  lint:
    runs-on: ubuntu-latest
    # ... (runs immediately)

  type-check:
    runs-on: ubuntu-latest
    # ... (runs in parallel with lint)

  test:
    needs: [lint, type-check]
    # ... (runs after both complete)
```

---

### ❌ Pitfall 3: Fixed Sleep Timers for Service Readiness

**Mistake:** `sleep 30` hoping service starts in 30 seconds.

**Fix:** Health check polling with timeout.

```bash
until curl -f http://localhost:1337/admin; do
  sleep 2
done
```

---

### ❌ Pitfall 4: Not Caching Dependencies

**Mistake:** Running `yarn install` from scratch every CI run (3-5 minutes).

**Fix:** Use GitHub Actions cache for node_modules.

```yaml
- uses: actions/setup-node@v4
  with:
    node-version: "20"
    cache: "yarn" # Caches node_modules automatically
```

---

### ❌ Pitfall 5: Ignoring Turborepo Cache in CI

**Mistake:** Turborepo caching works locally but not used in CI.

**Fix:** Persist `.turbo` cache between CI runs.

```yaml
- uses: actions/cache@v3
  with:
    path: .turbo
    key: turbo-${{ github.sha }}
    restore-keys: turbo-
```
