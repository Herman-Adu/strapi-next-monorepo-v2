## Understanding the Requirements

Before we build, let's understand the dependency chain:

```
PostgreSQL (port 5432)
    ↓ (must be ready before)
Strapi API (port 1337)
    ↓ (must be healthy before)
Next.js UI (port 3000)
```

**Key Challenges:**

1. **Docker availability:** Is Docker Desktop running? (No way to auto-start on all platforms)
2. **Database readiness:** PostgreSQL takes 5-10 seconds to accept connections
3. **Strapi health:** Build + start takes 40-60 seconds
4. **Race conditions:** Starting UI before Strapi = connection errors
5. **Graceful shutdown:** Kill one process = kill all (no orphaned processes)

The solution? A Node.js orchestrator with **health check polling**.

## Part 1: Checking Docker Availability

First, verify Docker is running (we can't start it programmatically on all platforms):

```javascript
const { spawn } = require("child_process")

function checkDockerRunning() {
  return new Promise((resolve) => {
    const docker = spawn("docker", ["info"], { stdio: "ignore" })

    docker.on("close", (code) => {
      resolve(code === 0)
    })
  })
}
```

**Why this works:**

- `docker info` returns exit code 0 if Docker daemon is running
- Exit code 1 if Docker Desktop isn't started
- `stdio: "ignore"` suppresses verbose output
- Returns a clean boolean Promise

---

## Part 2: Starting the Database

Once Docker is confirmed, start PostgreSQL via Docker Compose:

```javascript
function startDockerDatabase() {
  return new Promise((resolve, reject) => {
    const db = spawn("docker", ["compose", "up", "-d", "db"], {
      shell: true,
      stdio: "inherit",
    })

    db.on("close", (code) => {
      if (code === 0) {
        // Wait 3 seconds for PostgreSQL to initialize
        setTimeout(() => resolve(), 3000)
      } else {
        reject(new Error(`Database failed to start (exit code ${code})`))
      }
    })

    db.on("error", reject)
  })
}
```

**Key decisions:**

- `-d` flag = detached mode (runs in background)
- `stdio: "inherit"` = show Docker output (useful for debugging)
- 3-second wait = empirical testing showed PostgreSQL needs 2-3s to accept connections
- Error handling for missing docker-compose.yml

## Part 3: The Health Check Pattern

Here's where it gets interesting. We need to verify Strapi is **healthy**, not just **started**.

### HTTP Health Check

```javascript
const http = require("http")

function checkStrapiRunning() {
  return new Promise((resolve) => {
    const req = http.get(
      {
        hostname: "localhost",
        port: 1337,
        path: "/admin",
        timeout: 1000,
      },
      (res) => {
        resolve(res.statusCode === 200)
      }
    )

    req.on("error", () => resolve(false))
    req.on("timeout", () => {
      req.destroy()
      resolve(false)
    })
  })
}
```

**Why `/admin` instead of just checking the port?**

- Port 1337 might be listening, but Strapi could still be building
- `/admin` endpoint only responds when Strapi is **fully initialized**
- 1-second timeout prevents hanging if Strapi crashes

### Polling Loop with Exponential Backoff

```javascript
function waitForStrapi() {
  return new Promise((resolve, reject) => {
    const maxAttempts = 60 // 2 minutes max
    const interval = 2000 // Check every 2 seconds
    let attempts = 0

    async function check() {
      attempts++

      if (attempts > maxAttempts) {
        reject(new Error("Strapi failed to start after 2 minutes"))
        return
      }

      const isRunning = await checkStrapiRunning()

      if (isRunning) {
        log("✅ Strapi is ready!\n", colors.green)
        resolve()
      } else {
        // Show progress every 5 attempts (10 seconds)
        if (attempts % 5 === 0) {
          log(
            `⏳ Waiting for Strapi... (attempt ${attempts}/${maxAttempts})`,
            colors.yellow
          )
        }
        setTimeout(check, interval)
      }
    }

    check()
  })
}
```

**Pattern breakdown:**

1. **Max attempts:** 60 × 2s = 2-minute timeout (Strapi usually takes 40-60s)
2. **Interval:** 2 seconds between checks (not too aggressive, not too slow)
3. **Progress logging:** Every 10 seconds (prevents console spam)
4. **Recursive check:** `setTimeout(check, interval)` creates polling loop
5. **Early exit:** Resolves as soon as Strapi is healthy

This is the **same pattern** from [Part 1: 98% CI/CD Success Rate](./1.1-98-percent-ci-success-rate.md#strategy-4-health-check-polling) that improved our CI/CD reliability!

## Part 4: Starting Processes in Order

Now we orchestrate the startup sequence:

```javascript
function startStrapi() {
  return new Promise((resolve, reject) => {
    log("🚀 Starting Strapi backend...", colors.blue)

    const strapi = spawn(
      "yarn",
      ["workspace", "@repo/strapi", "run", "develop"],
      {
        shell: true,
        stdio: ["ignore", "pipe", "pipe"],
      }
    )

    // Forward stdout/stderr with prefix
    strapi.stdout.on("data", (data) => {
      const message = data.toString()
      process.stdout.write(`${colors.blue}[Strapi]${colors.reset} ${message}`)
    })

    strapi.stderr.on("data", (data) => {
      const message = data.toString()
      process.stderr.write(`${colors.blue}[Strapi]${colors.reset} ${message}`)
    })

    // Resolve after 2 seconds (don't wait for Strapi to close)
    setTimeout(() => resolve(strapi), 2000)

    strapi.on("error", reject)
  })
}

function startUI() {
  log("⚛️  Starting Next.js UI...", colors.cyan)

  const ui = spawn("yarn", ["workspace", "@repo/ui", "run", "dev"], {
    shell: true,
    stdio: "inherit", // Show Next.js output directly
  })

  return ui
}
```

**Key decisions:**

- **Prefixed output:** `[Strapi]` prefix helps debug which service logged what
- **stdio handling:** Strapi = pipe (for prefixing), Next.js = inherit (already has nice formatting)
- **Don't wait for close:** Strapi runs indefinitely; we just need the process handle
- **Return process handles:** Needed for graceful shutdown later

## Part 5: The Complete Orchestration Flow

```javascript
async function main() {
  try {
    log("🎯 Development Environment Orchestrator\n", colors.bright)

    // Step 1: Check Docker
    log("1️⃣  Checking Docker status...", colors.yellow)
    const dockerRunning = await checkDockerRunning()
    if (!dockerRunning) {
      log("❌ Docker is not running!", colors.red)
      log("   Please start Docker Desktop and try again.", colors.red)
      process.exit(1)
    }
    log("✅ Docker is running\n", colors.green)

    // Step 2: Start database
    log("2️⃣  Starting database...", colors.yellow)
    await startDockerDatabase()

    // Step 3: Start Strapi
    log("3️⃣  Starting Strapi...", colors.yellow)
    const strapiProcess = await startStrapi()

    // Step 4: Wait for Strapi health check
    log("4️⃣  Waiting for Strapi to be ready...", colors.yellow)
    await waitForStrapi()

    // Step 5: Start UI (only after Strapi is healthy!)
    log("5️⃣  Starting UI...", colors.yellow)
    const uiProcess = startUI()

    log("\n✅ All services started successfully!\n", colors.green)
    log("📍 Strapi Admin: http://localhost:1337/admin", colors.cyan)
    log("📍 Next.js UI:   http://localhost:3000", colors.cyan)
    log("\n💡 Press Ctrl+C to stop all services\n", colors.yellow)

    // Graceful shutdown
    const cleanup = () => {
      log("\n🛑 Shutting down services...", colors.yellow)
      if (strapiProcess && !strapiProcess.killed) {
        strapiProcess.kill("SIGTERM")
      }
      if (uiProcess && !uiProcess.killed) {
        uiProcess.kill("SIGTERM")
      }
      process.exit(0)
    }

    process.on("SIGINT", cleanup) // Ctrl+C
    process.on("SIGTERM", cleanup) // Kill command
  } catch (error) {
    log(`\n❌ Error: ${error.message}`, colors.red)
    process.exit(1)
  }
}

main()
```

**Flow breakdown:**

1. ✅ Verify Docker (exit early if not running)
2. ✅ Start PostgreSQL (wait 3s for initialization)
3. ✅ Start Strapi (get process handle)
4. ✅ **Wait for Strapi health check** (critical step!)
5. ✅ Start Next.js UI (safe now because Strapi is ready)
6. ✅ Graceful shutdown on Ctrl+C

**Why this order matters:**

- Starting UI before Strapi = connection errors
- Health check ensures Strapi is **fully initialized**, not just started
- Graceful shutdown prevents orphaned processes

## Troubleshooting

### "Docker is not running" error

**Cause:** Docker Desktop not started  
**Fix:** Start Docker Desktop manually, then run `yarn dev`  
**Note:** Auto-starting Docker is platform-specific and requires admin permissions

### Strapi timeout after 2 minutes

**Cause:** Strapi build errors or dependency issues  
**Fix:** Run `yarn workspace @repo/strapi develop` manually to see full error logs  
**Common culprits:** Missing `.env` file, database connection issues, npm install needed

### Port 1337 or 3000 already in use

**Cause:** Previous processes not killed  
**Fix:**

```bash
# Find and kill process on port 1337
npx kill-port 1337

# Find and kill process on port 3000
npx kill-port 3000
```

### UI starts but shows connection errors

**Cause:** Health check passed but Strapi restarted  
**Fix:** Increase `waitForStrapi` max attempts or add additional health check after Strapi startup  
**Long-term:** Implement retry logic in UI API client

## Reusability: Adapting This Pattern

This orchestrator pattern works for **any multi-service environment**:

### Microservices Architecture

```javascript
async function main() {
  await startDatabase()
  await startAuthService()
  await waitForService("http://localhost:5000/health")
  await startAPIGateway()
  await waitForService("http://localhost:8080/health")
  await startFrontend()
}
```

### Distributed Systems

```javascript
async function main() {
  await startRedis()
  await startKafka()
  await startWorkers()
  await startAPIServer()
  await startWebApp()
}
```

### Testing Environments

```javascript
async function main() {
  await startTestDatabase()
  await seedTestData()
  await startMockAPI()
  await waitForService("http://localhost:4000/ready")
  await runE2ETests()
}
```

**Universal principles:**

1. **Health checks over port checks** (ensure readiness, not just startup)
2. **Exponential backoff** (prevent overwhelming services during startup)
3. **Graceful shutdown** (kill all processes on Ctrl+C)
4. **Clear logging** (show progress, not spam)
5. **Fail fast** (exit early if dependencies missing)
